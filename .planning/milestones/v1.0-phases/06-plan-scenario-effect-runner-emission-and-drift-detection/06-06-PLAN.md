3. **`ParsedScenario.name` is the INTERPOLATED Pickle name and is the `it.effect` title**; `astName` is the un-interpolated scope key and is not (`Model.ts:124-129`). A Scenario Outline therefore emits one distinctly-titled test per Examples row.
4. **`ParsedFeature.scenarios` holds only FEATURE-LEVEL scenarios; `ParsedFeature.rules[].scenarios` holds the rule-nested ones; `allScenarios` is the flat union in document order** (`Model.ts:183-186`). The nesting walk uses the first two; `Plan.ts` built its `scenarios` array off `allScenarios`, so look plans up by `ParsedScenario.id`.
5. **A `describe` callback must be invoked SYNCHRONOUSLY and must never be `async`** — an async callback registers nothing and the Feature passes with zero tests (`describeFeature.ts:38-43` note (c)). `TestApi.describe`'s `define` is typed `() => void` precisely so this cannot be written.

Imports: `import type * as Layer from "effect/Layer"`, `import * as Effect from "effect/Effect"`,
`import type { TestApi } from "./TestApi.ts"`, `import type { FeaturePlan, ScenarioPlan } from "./Plan.ts"`,

parameter — that is the entire point of the seam, and an acceptance grep enforces it.

Export one function:
`export const emitFeature = (args: { readonly api: TestApi; readonly plan: FeaturePlan; readonly layer: Layer.Layer<any, any, never> }): void`

Structure of the walk:

1. Build a `Map<string, ScenarioPlan>` keyed on `scenarioId` from `plan.scenarios`, once, before emitting. `Plan.ts` produced its array off `feature.allScenarios`, and this walk re-derives the Feature/Rule nesting from `feature.scenarios` and `feature.rules`; the map is how the two views are joined. A `ParsedScenario` with no entry in the map is unreachable by construction — throw an `Error` naming the scenario id and saying it is a bug in `Plan.ts` or `Runner.ts`, following `Registry.ts:99-105`'s preferred "throw with an explanation" over a non-null assertion under `noUncheckedIndexedAccess`.

2. Call `api.describe(plan.feature.name, () => { ... })` exactly once. Everything else is emitted inside that callback, synchronously. The callback is a plain arrow returning `void` — never `async`, per verified fact 5.

3. Inside it, emit `plan.feature.scenarios` in array order, each as `api.effect(scenarioPlan.name, () => buildScenarioEffect({ plan: scenarioPlan, layer: args.layer }))`. Pass a THUNK: `buildScenarioEffect` must be called when the test runs, not while the block is being collected, so a Scenario's Layer is not built during collection.

4. Then, for each `rule` of `plan.feature.rules` in array order, call `api.describe(rule.name, () => { ... })` and emit that rule's `rule.scenarios` inside it, the same way. Rules come after feature-level scenarios because that is the order `ParsedFeatureCore` lists them and the order the document has them; do not interleave or sort.

5. Finally, still inside the Feature's `describe` callback, emit one node per `plan.warnings` — see Task 1b below. Emit them LAST so the Feature's real Scenarios keep the top of the block; say so in a comment, since "put the warnings first, they are more visible" is the plausible reversal.

**The warning node (CONTEXT.md D-02 channel 2).** For each `UnusedStepDefinitionWarning`, call
`api.effect(title, () => Effect.void)` — an always-passing test, never a failing or skipped one:
ADR-EC-019 makes an unused pattern a warning and not a failure, and a `skip` would make the count
of skipped tests a lie. Build `title` as
`` `⚠ unused step definition: ${warning.keyword} ${JSON.stringify(warning.pattern)} (${Option.getOrElse(warning.definedAt, () => "an unrecorded location")})` ``
— the keyword and site are included so two identical pattern strings registered at two sites cannot
produce two identically-titled test nodes, which `vitest/no-identical-title` and the vitest reporter
both handle badly. Note that in a comment.

Write the module doc comment in house format, opening with the statement that this is the ONLY
module whose job is emission and that it reaches `describe`/`it.effect` exclusively through the
injected `TestApi`. Lettered notes for at least: (a) why no vitest import may ever appear here,

inside `layer(...)`'s callback compiles and silently loses the shared Layer's services, which
becomes live in Phase 10; (b) why `buildScenarioEffect` is called inside a thunk rather than eagerly

`ParsedScenario.name` (interpolated) is the title and `astName` is not. Close with the paragraph

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Feature / Rule / Scenario names from a `.feature` file → vitest test titles | Author-controlled strings become test node names rendered by the reporter and, in some CI setups, written into JUnit XML or JSON report artifacts. |
| step definition pattern text → the warning node title | Author-controlled pattern text becomes a test title. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-06-01 | Tampering | pattern text embedded in a test title | mitigate | The pattern is rendered with `JSON.stringify` inside the warning title, so a pattern containing a quote or a newline cannot forge what looks like a second test node in the reporter's output. Escaping the Feature/Scenario names is deliberately NOT done — they must render exactly as the author wrote them, which is the whole point of the title. |
| T-06-06-02 | Denial of Service | duplicate test titles | mitigate | The warning node's title includes the keyword and the definition site, so two identical pattern strings at two sites do not collide. Scenario titles use the interpolated Pickle name, which a Scenario Outline makes distinct per Examples row — mutation record B is the standing proof that using `astName` instead would collapse them. |
| T-06-06-03 | Repudiation | a Feature that emits zero tests and passes | mitigate | `TestApi.describe`'s `define` is typed `() => void`, so an `async` callback cannot be written (verified fact 5), and Task 2's positional assertions fail if the expected `effect` records are absent. This is the exact "green suite that asserted nothing" failure `describeFeature.ts` note (c) exists to prevent, carried one layer down. |
| T-06-06-04 | Information Disclosure | absolute definition-site paths in a test title | accept | The site is a path on the developer's own machine, already present in the error messages plan 06-04 produces and in every stack trace the toolchain prints. If a CI job publishes its report artifact publicly, it is already publishing stack traces; this adds no new class of disclosure. |
| T-06-06-SC | Tampering | package-manager installs | accept | This plan installs nothing. `pnpm-lock.yaml` and every `package.json` are unmodified; `pnpm install --frozen-lockfile` must continue to succeed unchanged. |
</threat_model>
