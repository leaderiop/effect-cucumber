<objective>
Compose one `Effect` per Scenario: Background steps first, then the Scenario's own steps, as
sequential `yield*`s inside one `Effect.gen`, short-circuiting on the first failure, with the
Feature's Layer provided fresh. This is ADR-EC-004 and INV-EC-001 made executable, and it closes
roadmap success criteria 1 and 2.

Purpose: `Plan.ts` handed downstream a list of fully-resolved value objects. This module turns one
such list into one Effect and nothing else — no matching, no scope lookup, no vitest. Keeping it
that small is what makes INV-EC-001 assertable with a `Ref` counter and no test framework
machinery.

Output: `packages/vitest/src/ScenarioEffect.ts` and its test file.
</objective>

<verified_facts>
1. **Background steps are ALREADY first in `ParsedScenario.steps`**, read off `pickle.steps` by `Correlate.ts` (`Model.ts:137-141`: "do not re-stack Background steps"). `Plan.ts` preserves that order. This module must NOT reorder, filter by `origin`, or partition the list — it iterates it as given.
2. **A step body is already `(...args) => Effect`.** `Step.ts`'s `register` normalised it at registration time (the `Effect.fn` auto-wrap, ADR-EC-005). This module must never re-wrap: wrapping an already-wrapped body is not a compile error and not a test failure, it is a duplicated span, and `Step.ts` note (a) records that the only guard is a reference-identity assertion.
3. **`FeatureCollection.layer` is already the single merged Layer** (`describeFeature.ts:89-108`, `normalizeLayer`). This phase provides it fresh per Scenario, uniformly, with no shared/per-Scenario distinction at runtime — that distinction is Phase 10's entire reason to exist (RUN-03/RUN-04, ADR-EC-018). Do not add a shared path here.
4. **`@effect/vitest`'s `it.effect` supplies `Scope.Scope`.** After `Effect.provide(layer)` the Scenario Effect's remaining requirement is exactly `Scope.Scope`, which is what `TestApi.effect` (06-03) declares.
</verified_facts>

Create `packages/vitest/src/ScenarioEffect.ts`.

Imports: `import * as Effect from "effect/Effect"`, `import type * as Layer from "effect/Layer"`,
`import type * as Scope from "effect/Scope"`, and `import type { ScenarioPlan } from "./Plan.ts"`.
Submodule namespace imports only. Nothing from `vitest` or `@effect/vitest` — this module has no
business knowing a test framework exists.

Export one function with an explicit return annotation (`composite: true` requires it for
declaration emit):

`export const buildScenarioEffect = (args: { readonly plan: ScenarioPlan; readonly layer: Layer.Layer<any, any, never> }): Effect.Effect<void, unknown, Scope.Scope>`

Body: a single `Effect.gen(function*() { ... })` containing a `for (const planned of args.plan.steps)`
loop. For an `Unresolved` step, `return yield* Effect.fail(planned.error)`. For a `Resolved` step,
`yield* planned.step.body(...planned.step.args)` and discard the result.

A `for` loop of `yield*` inside ONE `Effect.gen` is the construction, and the short-circuit is
structural: the generator simply stops advancing after the first failure. Do NOT use
`Effect.forEach`, `Effect.all`, or an array `reduce` over `Effect.flatMap` — the loop is what makes
INV-EC-001 ("fail-fast is structural, not bookkept") literally true rather than a property that has
to be maintained. Do not add a `try`/`catch`, a `catchAll`, or any per-step recovery: a failing step
must reach the Scenario's error channel unmodified, which is what `it.effect` reports.

Do not call `Effect.fn` or `Effect.withSpan` on the step body. Verified fact 2: it is already
wrapped, and re-wrapping produces a duplicated span that nothing catches.

Provide the Layer at the end with `.pipe(Effect.provide(args.layer))`, so the returned Effect's
remaining requirement is `Scope.Scope` alone. Provide it ONCE, around the whole Scenario Effect,
never per step — a per-step provision would rebuild the Layer for every step and give each step a
different `World` instance, which is a silent behavioural bug rather than a compile error.

The `any`s in `Layer.Layer<any, any, never>` are erased detail, matching `FeatureCollection.layer`'s
existing declaration: `Dsl.ts`'s `StepRegistrar<ROut>` has already checked every step body against
the ambient Layer's output at authoring time, and this type never appears in a position a caller
writes against. Say so in a doc comment, pointing at `describeFeature.ts:61-70`'s equivalent note
so the two do not diverge.

Write the module doc comment in house format with a prose opener naming this as the ScenarioEffect
stage, then lettered notes for at least: (a) why the `for`-loop-of-`yield*` and not a combinator —
INV-EC-001 is structural, and naming `Effect.forEach` as the plausible tidy-up that would make it
bookkept; (b) why the Layer is provided once around the whole Scenario and never per step, naming
the silent-different-`World` failure; (c) why an `Unresolved` step becomes an `Effect.fail` IN
POSITION rather than an up-front rejection — ADR-EC-019 fails the containing Scenario, not the
file, and ARCHITECTURE.md Anti-Pattern 2 forbids doing the matching inside the running Effect,
which this is not: the matching already happened at Plan time and only the verdict is deferred.
Close with the paragraph naming allowed local imports (`./Plan.ts` only, type-only) and barrel
status (internal, not exported from `index.ts`).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| planned step body → the running Effect | Arbitrary developer-supplied code is executed with developer-supplied arguments. |
| Feature Layer → every step in the Scenario | One Layer's services are shared across all steps of one Scenario execution. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-05-01 | Elevation of Privilege | executing `planned.step.body` | accept | Running the developer's own step definitions in their own test process is the product's entire purpose. There is no privilege boundary to elevate across: the code, the arguments and the process all belong to the same developer. Sandboxing a test runner would defeat it. |
| T-06-05-02 | Tampering | state leaking between Scenarios via a memoised Layer | mitigate | `Effect.provide` is applied once per Scenario Effect and the Layer is rebuilt on each execution. Task 2's freshness test observes a BUILT value across two runs rather than comparing Layer object references — `Registry.ts:17-21` records why reference inequality alone is not proof. Mutation record C is the standing guard against moving the provision. |
| T-06-05-03 | Denial of Service | a step body that never completes | accept | An infinite or hanging step is bounded by vitest's own per-test timeout, which the `TestApi.effect` seam passes through unchanged. Adding a second timeout here would fight the framework's and produce two competing failure messages. |
| T-06-05-04 | Repudiation | a swallowed step failure | mitigate | No `catchAll`, `catchTag`, `orElse` or `try`/`catch` appears in this module — asserted by grep — so a failure reaches `it.effect`'s reporter unmodified. Task 2 asserts the squashed cause is reference-equal to the value the step failed with. |
| T-06-05-SC | Tampering | package-manager installs | accept | This plan installs nothing. `pnpm-lock.yaml` and every `package.json` are unmodified; `pnpm install --frozen-lockfile` must continue to succeed unchanged. |
</threat_model>
