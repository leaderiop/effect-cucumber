<objective>
Implement ADR-EC-007's second correction literally: **custom parameter types are data, not a live
registry.** A call that defines one appends a plain `{ name, regexp, transform }` record to an array
this library owns; nothing touches a `ParameterTypeRegistry` at definition time. Every consumer that
needs a registry builds a **fresh** one and replays every recorded record into it.

That single design decision closes the whole failure class the original correction was
self-contradictory about: a fresh registry has nothing registered into it yet, so re-acquiring the
eleven built-ins can never collide; and because replay happens on every build, a definition added at
module scope is correctly present in every subsequent build rather than landing once in a registry
that no longer exists.

Two rejections are added on top of the ADR, both at DEFINITION time so the error points at the
caller's own code rather than at a replay deep inside `loadFeature`: a name that collides with one of
the registry's built-ins, and a name defined twice in the same store.

Purpose: MATCH-02, roadmap success criteria 2 and 3.
Output: `src/ParameterTypes.ts` and `test/ParameterTypes.test.ts`.
</objective>

  | "BuiltInParameterTypeName" | "DuplicateParameterTypeName" | "IllegalParameterTypeName"
  | "InvalidParameterTypeRegexp" | "InvalidParameterTypeDefinition" | "UndefinedParameterType"

export class StepPatternError extends Error {
  readonly _tag: "StepPatternError"
  readonly reason: StepPatternErrorReason
  readonly parameterTypeName: string | undefined
  readonly pattern: string | undefined
  constructor(args: { reason; parameterTypeName?; pattern?; message; cause? })
}

class ParameterTypeRegistry {
  constructor()                                    // pre-registers 11 built-ins
  get parameterTypes(): IterableIterator<ParameterType<unknown>>
  lookupByTypeName(typeName: string): ParameterType<unknown> | undefined

    preferForRegexpMatch?: boolean,
    builtin?: boolean
  )
}

    `define` validates in this exact order, raising a `StepPatternError` with `parameterTypeName` set
    and a message shaped `<reason>: <what to do>`:

       `builtInParameterTypeNames`, and tells the caller to choose a different name. This check is
       FIRST and is the reason the empty-string anonymous name is rejected too.
    2. the name is already present in this store -> reason `DuplicateParameterTypeName`. The message
       names the parameter type and BOTH definition sites: the recorded `definedAt` of the first

       `"an unrecorded location"` when absent. Never let upstream's

       `try`/`catch`. Any throw that survives the four checks above becomes reason
       `InvalidParameterTypeDefinition` with the caught value forwarded as `cause`. This exists so an
       upstream change surfaces as a named library error rather than a raw
       `CucumberExpressionError`.

    Only after all five pass does `define` append the record and remember the name. `define` returns
    `void` and mutates only the closed-over store — it must never touch a `ParameterTypeRegistry`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller's `define` call → this library's stored records | Caller-supplied name, regexp source and transform function all cross here; the transform is arbitrary caller code this library will later invoke |
| stored records → a freshly built `ParameterTypeRegistry` | Replay is where an upstream throw would otherwise escape unnamed; it runs inside `loadFeature`, far from the caller's `define` call |
| caller-supplied `RegExp` → the regular expression a step text is matched against | A catastrophically backtracking custom regexp runs against feature-file text on the dev/CI machine |

| T-03-11 | Tampering | cross-call registry state — the failure class Pitfall 14 documents across three cypress-cucumber-preprocessor issues | mitigate | `define` never touches a registry; `buildRegistry` constructs a fresh `ParameterTypeRegistry` every call.
