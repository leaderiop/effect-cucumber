<objective>
Lay the two leaves this phase's implementation modules build against: the typed failure surface for
step patterns and parameter types, and an upstream-behaviour pin for
`@cucumber/cucumber-expressions@20.1.0`.

The pin exists for the same reason `upstream-pin.test.ts` exists for `@cucumber/gherkin@42`: when it
fails, a dependency changed its semantics, and that failure is attributable to the dependency rather
than to this library's code. Every non-obvious claim the rest of Phase 3 is built on — eleven
built-ins pre-registered by the constructor, a duplicate-name throw, a construction-time throw for an
unregistered `{customType}`, no ambiguity detection across two step patterns, an unwrapped Promise
out of an async transform — is verified upstream behaviour that must not be assumed silently.

Purpose: MATCH-01 and MATCH-02 both need a named error at declaration time rather than a raw
`CucumberExpressionError`, and both need the upstream contract written down.
Output: `StepPatternError` in `src/Errors.ts`, `test/expressions-pin.test.ts`, and new
`StepPatternError` pins in `test/Contracts.test.ts`.
</objective>

Barrel exports (dist/index.d.ts):
  Argument, CucumberExpression, CucumberExpressionGenerator, Expression, ExpressionFactory,
  GeneratedExpression, Group, Located, Node, NodeType, ParameterType, ParameterTypeRegistry,
  RegExps, RegularExpression, StringOrRegExp, Token, TokenType

NOT exported from the barrel: CucumberExpressionError, UndefinedParameterTypeError,
AmbiguousParameterTypeError. They are reachable only by a deep path into dist/. Discriminate
structurally (an UndefinedParameterTypeError carries a string `undefinedParameterTypeName`
property), never by instanceof against a deep import and never by message text.

new ParameterTypeRegistry() pre-registers 11 names, in this iteration order:
  "int", "float", "word", "string", "", "double", "bigdecimal", "byte", "short", "long", "biginteger"

Runtime types produced by each built-in (verified):
  int -> number     float -> number   word -> string    string -> string (quotes stripped)
  double -> number  bigdecimal -> string   byte -> number   short -> number
  long -> number    biginteger -> bigint   "" (written {}) -> string

ParameterType.isValidParameterTypeName(name): false only when the name contains one of
  [ ] ( ) $ . | ? * +
after unescaping. NOTE the thrown message names a DIFFERENT set of characters than the pattern
actually rejects — the message says "{, }, (, ), \ or /" while ILLEGAL_PARAMETER_NAME_PATTERN is
/([[\]()$.|?*+])/. "a/b" and "{bad}" both pass. Pin the real behaviour, not the message.

ParameterType constructor throws CucumberExpressionError for a RegExp carrying any of the flags
g, i, m, y. Message form: "ParameterType Regexps can't use flag 'i'".

registry.defineParameterType(pt) throws CucumberExpressionError
  "There is already a parameter type with name int" on a name collision, built-ins included.

new CucumberExpression("a {money} b", registry) throws AT CONSTRUCTION (not at match) with
  UndefinedParameterTypeError, .undefinedParameterTypeName === "money".

expression.match(text) returns readonly Argument[] | null. null means no match.
Argument.getValue(thisObj) returns the transform result UNWRAPPED — an async transform yields a
real Promise, and a throwing transform throws synchronously out of getValue.

Expressions are anchored (^...$). "apple(s)" is an optional group, "happy/sad" is an alternation,
and neither produces an argument. A backslash before "{" escapes the whole parameter:
"a \{int} b" compiles to /^a \{int\} b$/ and yields zero arguments.

Two step patterns both matching one step text is NOT detected by this package:
  "I have {int} apples".match("I have 5 apples")  -> [5]    (number)
  "I have {word} apples".match("I have 5 apples") -> ["5"]  (string)
