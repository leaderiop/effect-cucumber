<objective>
Wire the phase together and prove the lifecycle end to end.

`ParameterTypes.ts` and `StepMatcher.ts` are correct in isolation but unreachable: nothing calls
`buildRegistry`, and the package barrel still exports only the parse surface. This plan closes both
gaps and delivers roadmap success criterion 2, which is a statement about `loadFeature` specifically:
a custom parameter type declared once as data must resolve in TWO separate `loadFeature` calls in the
same process, with no duplicate-registration throw on the second.

Two contract changes fall out, and both are additive:
`ParsedFeature` gains a `parameterTypes` field — the join point Phase 6's `Plan` needs to hand a
registry to `createStepMatcher` — and `loadFeature`/`parseFeature` gain an optional trailing options
argument carrying a store override, which is what lets a test be hermetic against an append-only
module-level default store.

Purpose: MATCH-02 (roadmap success criterion 2), and MATCH-01's public reachability.
Output: the `parameterTypes` field, the fresh-registry-per-call wiring, the real barrel, and
`test/ParameterTypeLifecycle.test.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `@effect-cucumber/gherkin` → `@effect-cucumber/vitest` | The package barrel is the only cross-package edge; anything not exported here is unreachable in Phase 6, and anything exported becomes public API |
| module-level default store → every `loadFeature` call in the process | An append-only process-wide store is written once and read by every call thereafter; a test that writes to it changes later tests' behaviour |
| `ParsedFeature` shape → Phases 5 and 6 | This contract is already consumed downstream; a non-additive change breaks a package that has not been written yet |
