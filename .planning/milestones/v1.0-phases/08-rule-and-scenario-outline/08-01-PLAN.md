<objective>
Give the scope chain a fourth, middle level: a registration made at Rule scope, or inside a Rule's
own Background, is visible only to Scenarios inside that specific Rule — never to a different Rule,
never to a Feature-level Scenario, and never (for the Background half) to the Feature's own
Background.

Purpose: `Plan.ts` note (e) has stated since Phase 6 that `RegistryScopeKind` is `feature | background
| scenario` and that only the REGISTRATION surface for Rule scope is missing (ARCHITECTURE.md Pattern
5's three-level chain — Scenario → Rule → Feature — already resolves correctly for READING). This plan
closes that gap at the data-model and matching layer, ahead of the DSL surface (08-03) and the
composition root (08-05a) that will register through it. Getting the identity check right here —
comparing a resolved Rule id, never an author-typed name, and reserving `null` exclusively for "not
nested in any Rule" — is what makes DSL-05's compile-time boundary (proved later by 08-06's tsgo-gate
fixtures) also true at runtime, and what INV-EC-005 needs to hold when two Rules share a name.
Output: `Registry.ts`'s extended scope type, `Plan.ts`'s rule-aware visibility and three-level rank,
`Registry.test.ts`/`Plan.test.ts` extended to prove isolation and precedence, and `Runner.test.ts`'s
own `RegistryScope`-literal helper kept compiling against the new required field.
</objective>

  export type RegistryScopeKind = "feature" | "background" | "scenario" | "rule"
  export type RegistryScope = { readonly kind: RegistryScopeKind; readonly name: string | null; readonly ruleId: string | null }

INVARIANT a later plan (08-05a) must honor when constructing a RegistryScope:
  `ruleId` is `null` if AND ONLY IF the scope is NOT nested inside any `Rule(...)` call. A scope
  pushed from inside `Rule(name, extraLayer, define)` always carries a non-null string — either the
  real `ParsedRule.id` this Rule's name resolved to, or a sentinel string that can never equal a real
  scenario's `ruleId` (for the case the author's Rule name does not match any Rule in the parsed
  Feature). Registry.ts itself performs NO resolution — it has zero imports (note (c)) — the caller
  supplies whatever string it has already resolved.
