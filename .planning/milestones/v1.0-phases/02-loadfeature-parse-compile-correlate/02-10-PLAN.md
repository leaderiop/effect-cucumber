<objective>
Turn two Phase 2 conventions into mechanical gates.

The first is PARSE-01's STRUCTURAL proof. `02-RESEARCH.md` Pitfall P1 shows the behavioral form
(a module-top-level call plus exactly one `it`) is necessary but weak: it observes that
`loadFeature` contributed no tests. The structural form proves it by construction — a
`loadFeature` that cannot reach a test runner CANNOT register a test — and it simultaneously
guards ADR-EC-015, which forbids `@effect-cucumber/gherkin` from declaring `effect` in any
manifest field.

The second closes Decision D7, an open question Phase 1 explicitly deferred: `tsc -b` covers
`include: ["src"]` only, so test files are transpiled-but-not-checked by vitest and can be wrong
in ways CI never catches. Phase 2 is the first phase to write real test files, so it inherits the
decision. DECISION: yes, wire it.

STATE.md's rule from 01-06 is non-negotiable and governs both: every CI step is a root
`package.json` script that also runs locally, and adding a new gate script means adding a CI step
for it — "a script nobody runs is back to being a convention."

Purpose: makes the two structural claims of this phase unable to decay silently.
Output: one gate script, one tsconfig, two root scripts, two CI steps.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| package manifest → published dependency graph | A stray `effect` or `vitest` entry in `dependencies`/`peerDependencies` changes what every consumer is forced to install |
| `packages/gherkin/src` → runtime capability | An import of a test runner would give `loadFeature` the ability to register tests, silently violating PARSE-01 |
| local developer run → CI run | A command that exists only in CI (or only locally) lets the two diverge |

Mutation-tested against an injected `effect/Effect` import. |

Guards ADR-EC-015 mechanically. |
