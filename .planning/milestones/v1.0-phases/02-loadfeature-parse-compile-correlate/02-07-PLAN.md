    Create `packages/gherkin/src/Validate.ts`. Local imports: `./Correlate.ts`, `./Errors.ts`,
    `./Model.ts`. Never `./index.ts`.

    Open with a module doc comment stating (a) why this is a separate pass from `Correlate.ts` —
    several checks need the correlated view (an AST node PLUS its pickle set), so inlining them
    into the walk would make the walk both build and judge, and a fixture failure could no longer
    tell you which broke; and (b) that every check here exists because `@cucumber/gherkin` does
    the right thing for its own purpose (producing runnable pickles) and the wrong thing for ours
    (telling an author their feature file is broken).

    Export `validateFeature(result: CorrelationResult): ReadonlyArray<LoadFeatureWarning>`. It
    THROWS a `LoadFeatureError` on the first error found in document order, and returns the
    accumulated warnings otherwise. Throwing is the correct failure mode: BEH-EC-001's signature
    is `(path: string) => ParsedFeature`, a plain value, so a throw is the only in-signature
    failure. Deterministic document order matters — a fixture must be able to assert WHICH error
    fired.

    Implement these checks by iterating `index.astScenarios` in document order. For each node,
    look up its pickles via `index.byScenarioId` (a missing key yields an empty array) and
    compute `isOutline` via the exported `isOutlineKeyword(index.language, node.keyword)`:

    - If `isOutline` and `node.examplesCount === 0` (row F3): throw
      `reason: "OutlineWithoutExamples"` at the node's line. Verified: `compile()` takes the
      plain-Scenario branch and emits ONE pickle whose step text keeps its literal placeholders.
      This code path is distinct from F1/F2 and is not in PITFALLS.md.
    - Else if `isOutline` and the pickle array is empty (rows F1 and F2): throw
      `reason: "EmptyExamples"` at the node's line. Verified: an `Examples:` with no header row,
      or a header with no body rows, produces ZERO pickles and no upstream error, orphaning the
      AST node.
    - Else if not `isOutline` and `node.examplesCount > 0` (row F4): throw
      `reason: "ScenarioKeywordWithExamples"` at the node's line. Verified: `compile()` branches
      on `examples.length`, never on the keyword, so a plain `Scenario:` with an `Examples:`
      table silently compiles as an Outline.
    - For each pickle of the node, if `pickle.steps.length === 0` (rows F5 and F6): throw
      `reason: "ZeroStepScenario"` at the pickle's line. Verified: a zero-step Scenario produces
      one pickle with `steps: []` AND its Background steps are dropped too, at both feature and
      Rule level. The message MUST quote the AST node's `description` verbatim when it is
      non-empty, prefixed by an explanation that a step keyword typo written BEFORE any valid
      step is silently swallowed into the Scenario description (verified, position-dependent, and
      invisible at every layer). This is the cheap, high-signal mitigation for row F14/Pitfall P7
      and it turns the single most confusing case into a self-explaining one. Do not truncate the
      description.

    Every error message must be shaped `uri:line: <reason>: <what to do>` — the message quality
    matters because `loadFeature` is called at module top level, so a throw becomes a vitest
    COLLECTION error for the whole file.

    Use `isScenarioKeyword` where the negative of `isOutlineKeyword` is not precise enough for a
    dialect that has extra keyword forms; do not hardcode any English keyword string.

    DO NOT implement a check for a feature-level `Background:` written after a `Rule:`. Verified
    refutation: Gherkin's grammar forbids it outright and the parser throws
    `UnexpectedTokenException`, so PITFALLS.md Pitfall 30's premise is false and its recommended
    walk-time check is dead work. Record that decision in the module doc comment so nobody adds
    it later.

    Leave a clearly-marked extension point for the leftover-placeholder scan and the Group C
    warnings — plan 02-08 adds them to this same file.

    Add the duplicate-name check to `packages/gherkin/src/Validate.ts`. Both aspects below are
    LOCKED developer decisions, not recommendations — implement them exactly.

    LOCKED DECISION 1 (severity): a Feature containing two Scenarios with the same
    UN-INTERPOLATED name in the same scope is REJECTED with a `LoadFeatureError`, reason
    `DuplicateScenarioName`. Not a warning, not a rename, not positional fallback.

    LOCKED DECISION 2 (scope): uniqueness is PER SCOPE — feature level, or within one Rule. Two
    different Rules may each legally contain a `Scenario: happy path`. Whole-Feature uniqueness is
    explicitly rejected.

    Implement with one `Map` keyed on the pair `(ruleId ?? "<feature>", astName)`, populated while
    iterating `index.astScenarios` in document order. Key on the AST node's own un-interpolated
    name, NOT on `pickle.name` — an Outline's rows legitimately produce many interpolated names
    from one node, and comparing those would produce false collisions. Guard against duplicating
    a node: an Outline node appears once in `astScenarios` even though it yields N pickles.

    On the second occurrence of a key, throw `reason: "DuplicateScenarioName"` with the message
    naming the duplicated name, the scope (the Rule's name, or "the Feature"), and BOTH line
    numbers — the first occurrence's line and this one's. `line` on the error is the SECOND
    occurrence's line.

    Add a doc comment recording why this check exists at all: verified, two Scenarios named `dup`
    in one Feature parse fine and yield two pickles with identical names and distinct
    `astNodeIds`. Success criterion 4 and ARCHITECTURE.md Open Question 4 both match a Scenario to
    its registered definition by the un-interpolated name, and neither noticed that names are not
    unique. Rejecting here turns a Phase-6 design hole with no good runtime answer into an
    authoring-time error, which is this project's stated core value applied to one more axis.
    Also record that the per-scope choice mirrors Phase 6's per-scope scope-chain resolution
    (ARCHITECTURE.md Pattern 5).
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| correlated `ParsedFeatureCore` → author-facing error output | Validation decides what a feature-file author is told; a missed check becomes a false-green test |
| Scenario `description` content → error message | Author-written free text is reproduced verbatim in error output that may reach CI logs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-16 | Repudiation | silent-wrong `compile()` output producing a false-green test | mitigate | Each of rows F1-F6 and F22 raises a distinct, named, located `LoadFeatureError` in a dedicated validation pass, with one test per reason asserting `err.reason`. This is ADR-EC-019's "fail loudly" applied to the parse layer. |
| T-02-02 | Information Disclosure | Scenario `description` quoted verbatim in the `ZeroStepScenario` message | **accept** | Locked developer decision: full content, no truncation. The description is exactly where a swallowed leading-typo step lands, so quoting it is what makes the phase's most confusing failure self-explaining. Accepted tradeoff: author-written text reaches CI logs unredacted. |
| T-02-01 | Denial of Service | ReDoS via a feature-derived `RegExp` | mitigate | This plan's checks are structural comparisons and `Map` lookups only. Acceptance criterion asserts `new RegExp` count is 0 in `Validate.ts` at this stage; plan 02-08 introduces exactly one FIXED-LITERAL regex, matched against feature text (the safe direction). |
| T-02-17 | Tampering | dead-work check reintroduction (PITFALLS.md Pitfall 30) | mitigate | Verified refutation recorded in the module doc comment and enforced by an acceptance criterion, so a future contributor cannot add a Background-after-Rule walk check believing it is needed. |
</threat_model>
