<objective>
Build the three input-side modules: reading bytes, parsing them into a `GherkinDocument`, and
compiling that into pickles — with every upstream throw normalised into a `LoadFeatureError`
carrying one of the Group B reason tags. Then prove it with one test per reason.

Purpose: `02-RESEARCH.md`'s Pitfall P5 is that the cascading-error handler must survive two
distinct error shapes, and reading `.errors` unconditionally throws a `TypeError` while handling
a parse error — the worst possible place for a second bug. Getting this module right is what
turns a wall of nine cascading upstream errors into one message naming the real defect.
Output: `src/Source.ts`, `src/Parser.ts`, `src/Pickles.ts`, `test/Parser.test.ts`.
</objective>

    Import `{ AstBuilder, Errors, GherkinClassicTokenMatcher, Parser as GherkinParser }` from
    `"@cucumber/gherkin"` — `Errors` is a named export of the package index; do NOT deep-import
    `dist/Errors.js`. Import `IdGenerator` from `"@cucumber/messages"` (it is NOT re-exported by
    `@cucumber/gherkin`). Type-only imports use `import type`.

    Export `parseDocument(source: string, uri: string, newId: IdGenerator.NewId): GherkinDocument`.
    It constructs `new GherkinParser(new AstBuilder(newId), new GherkinClassicTokenMatcher())`
    and calls `parse(source)` inside a `try`/`catch`. Use `GherkinClassicTokenMatcher` only —
    `GherkinInMarkdownTokenMatcher` (Markdown feature files) is explicitly out of scope for this
    milestone; state that in the module doc comment so a future reader knows the omission was
    deliberate.

    The `newId` parameter is required, never defaulted inside this module. Decision D3: exactly
    one `IdGenerator.uuid()` per `loadFeature` call, shared by `AstBuilder` AND `compile`.
    Verified failure modes if that is violated: a fresh `incrementing()` per file makes two
    different Features both give their first Scenario the id `"1"`, corrupting any cross-file map;
    and independent generators for parse and compile give `scenario.id === "1"` and
    `pickle.id === "1"` in the same document, so `"1"` acquires two meanings.

    Error normalisation, the load-bearing part:
    - Normalise the caught value with the cucumber-js idiom `err.errors ?? [err]`. Two shapes
      exist and both must survive: with the default `stopAtFirstError === false` the throw is a
      `CompositeParserException` whose `.errors` is present and whose own `.location` is
      `undefined`; with `stopAtFirstError = true` the throw is a bare `UnexpectedTokenException`
      with NO `.errors` array and `.location` present. Reading `.errors` unconditionally throws a
      `TypeError` while handling a parse error.
    - Discriminate the classes with `instanceof Errors.CompositeParserException`,
      `instanceof Errors.NoSuchLanguageException`, etc. NEVER with `err.name`: verified, every
      one of those classes reports `.name === "Error"`, so a `.name` switch silently matches
      nothing.
    - If the FIRST normalised entry is an `Errors.NoSuchLanguageException`, throw a
      `LoadFeatureError` with `reason: "UnknownDialect"` — a distinct reason from `ParseFailed`.
      Take the line from that entry's `.location`.
    - Otherwise throw `reason: "ParseFailed"` with the line taken from the FIRST entry's
      `.location` (never from the composite, whose `.location` is `undefined`). Verified: one
      misplaced tag produced NINE errors, all variations of the same "expected: #TagLine,
      #RuleLine, #Comment, #Empty" covering the rest of the file. Report the first error
      prominently in the message and collapse the remainder into a trailing summary line naming
      how many further errors followed and their line numbers — the real defect is buried under
      eight consequences. Do not truncate any individual error's own text (the no-truncation
      policy from `Errors.ts` applies here too).
    - Set `cause` to the originally caught value in every case.

    After a successful parse, check `document.feature`. Verified: it is `undefined` (NOT `null`)
    for a comment-only file or an empty string. Write `document.feature === undefined` or a
    falsy check — `== null` will not lint, because `eqeqeq` is `"error"` in `.oxlintrc.json`
    (this is a direct conflict with 02-RESEARCH.md Pitfall P6's parenthetical, and the lint rule
    wins). Throw `reason: "NoFeature"` with no line.

    Also note in the doc comment that `GherkinDocument.uri` is `undefined` when parsing from a
    string — `Parser.parse(source)` never sets it — so every `uri` in this package comes from the
    caller, never from the document.

    Create `packages/gherkin/src/Pickles.ts`. Export
    `compilePickles(document: GherkinDocument, uri: string, newId: IdGenerator.NewId): ReadonlyArray<Pickle>`,
    a thin wrapper over `compile(document, uri, newId)` from `@cucumber/gherkin` that takes the
    SAME `newId` the document was parsed with. If `compile` throws, wrap it as
    `reason: "ParseFailed"` with `cause` set. Do not filter, sort, deduplicate, or otherwise
    transform the returned pickles — every silent-wrong case is detected in `Validate.ts`, over
    the correlated result, not here. Keep the module a single function so `import/no-cycle` and
    `pnpm circular` stay trivially satisfied.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller-supplied path → `fs.readFileSync` | The only filesystem access in the package |
| `.feature` bytes → `@cucumber/gherkin` `Parser` | All lexing, dialect handling, and error positioning is delegated upstream; this phase adds no custom lexer, no `eval`, no dynamic `RegExp` |
| upstream exception objects → `LoadFeatureError` | Untyped `unknown` values from a dependency cross into this package's typed error surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Tampering | `readFeatureSource(path)` in `src/Source.ts` | **accept** | The caller already controls the path and runs in their own process; no privilege boundary is crossed. Path sanitisation would be security theatre and is explicitly forbidden by an acceptance criterion (`resolve(`/`normalize(` must not appear). |
| T-02-04 | Denial of Service | cascading-error handling in `src/Parser.ts` | mitigate | Normalise with `err.errors ?? [err]` so neither error shape can raise a `TypeError` inside the catch block. Report the first error and collapse the remainder to a count plus line numbers, bounding output size on a file that produces the parser's ~10-error hard stop. |
| T-02-11 | Spoofing | error-class discrimination | mitigate | Upstream classes report `.name === "Error"`, so `.name`-based routing silently matches nothing and would misclassify `NoSuchLanguageException` as a generic `ParseFailed`. Enforced by `instanceof Errors.X` plus an acceptance criterion that `.name ===` never appears. |
| T-02-05 | Input Validation (V5) | `.feature` content | mitigate | 100% of parsing is delegated to `@cucumber/gherkin`. Acceptance criteria assert no `new RegExp`, no `eval`, and no custom lexer in these modules. |
| T-02-02 | Information Disclosure | parse-error message content | accept | Per the locked full-content policy, upstream error text is reproduced verbatim. Only the COUNT of cascading consequences is collapsed, never the content of any individual error. |
</threat_model>
