<objective>
Give `BeforeAllScenarios` and `AfterAllScenarios` a home, using only the `describe`/`effect` surface
`TestApi` already exposes.

Purpose: this is 07-CONTEXT.md's one open "Claude's Discretion" mechanism question. `emitFeature` is
the only place that knows a Feature has N Scenarios, which makes it the natural owner of a result
shared across all of them (D-08). 07-PATTERNS.md verified the primitives: `Deferred.makeUnsafe` is
synchronous and therefore constructible during the emission walk, `Effect.cached` is not (its memo is
only reachable by running an Effect first), and there is no `Effect.once` in this build.
Output: a once-cell prepended to every Scenario thunk, and a trailing always-run node for
`AfterAllScenarios` — with no change to `TestApi.ts`.
</objective>

    synchronous, which is the whole reason it fits an emission walk), a closure `started` boolean, and
    an `Effect.suspend` that on the first execution flips `started` and runs the body through
    `Deferred.into` so the deferred is completed with the body's exit, and on every later execution
    returns `Deferred.await(deferred)`. Give it an explicit return annotation — `composite: true`
    demands it, and pinning `Effect<void, unknown, Scope.Scope>` here keeps `any` out of the emitted
    contract.

    Document, in a doc comment on `makeOnce`, that the plain boolean is sound because vitest runs the
    tests of one file sequentially and each `it.effect` runs to completion before the next begins; and
    that `Deferred.await` on the second and later callers is what makes a FAILING
    `BeforeAllScenarios` reach every Scenario individually rather than only the first — D-08's literal
    requirement.

    (2) Compose the BeforeAllScenarios cell only when `hooks.BeforeAllScenarios` is non-empty:
    `makeOnce(runHookBatch(hooks.BeforeAllScenarios).pipe(Effect.provide(layer)))`. Providing the layer
    HERE, inside the cell, is deliberate: the cell must not depend on which Scenario happened to
    trigger it, and providing it inside the triggering Scenario's own composed Effect would bind the
    Feature-wide hook to Scenario one's Layer instance. Say that in a note.

    (3) Every `api.effect(scenarioPlan.name, …)` thunk in both Scenario loops becomes, when a cell
    exists, the cell sequenced ahead of the Scenario Effect — with the `buildScenarioEffect(...)` call
    INSIDE the sequencing callback (`Effect.flatMap`'s function body), never evaluated at emit time.
    Note (b) is explicit: composing eagerly moves Layer construction into collection for every Scenario
    in the file, including the ones a `-t` filter is about to skip. When no cell exists, the thunk is
    byte-for-byte what plan 07-04 left it as — a hookless Feature must emit exactly what it emitted
    before this plan. Keep the two loops written out separately at their two nesting depths; do not
    factor them into a shared helper (note in the existing file says why).

    (4) After the Rules loop and BEFORE the warnings loop, when `hooks.AfterAllScenarios` is non-empty,
    emit ONE extra node via `api.effect` whose body is
    `runHookBatch(hooks.AfterAllScenarios).pipe(Effect.provide(layer))`, bound to a `const` with an
    explicit `Effect<void, unknown, Scope.Scope>` annotation inside the thunk rather than left as a
    floating expression (`effect(floatingEffect)` rejects an Effect-valued expression statement).

    Its title is a CONSTANT string with no interpolation of any Feature, Rule or Scenario name:
    `⚙ AfterAllScenarios`. A constant title cannot be forged by a document's own text, which is the
    threat `warningTitle`'s `JSON.stringify` addresses on its own path.

    A separate emitted node — rather than a finalizer around something — is what makes D-09's "runs
    always" structural: it does not await the BeforeAllScenarios deferred, so a failed
    `BeforeAllScenarios` cannot stop it; and it is a sibling of the Scenario nodes, so a failed
    Scenario cannot stop it either. Emission order stays document order and is never sorted; running
    "always" is a runtime property of the emitted nodes, not a reordering. Write all of this as a
    numbered note in the module header, naming the plausible tidy-ups: "wrap the whole describe block
    in a finalizer instead" (there is nothing to wrap — `describe`'s callback returns `void`) and
    "emit it after the warnings" (note (c) says the warnings come last, and they are always-passing
    footnotes while this node can fail).

    Note (a)'s absolute rule survives: the string `vitest` must not appear anywhere in this file,
    comments included.
