  <action>
    Add `runHookBatch` to `packages/vitest/src/Hook.ts`, exported, with the signature
    `(hooks: ReadonlyArray<HookBody>) => Effect.Effect<void, unknown, any>`.

    Semantics, which are D-02 plus D-03 exactly:
    - Run every hook in the array, in array order (which is registration order — D-01), each to an
      `Exit` via `Effect.exit`. Every hook in the batch runs even when an earlier one failed: the
      batch is INDEPENDENT, deliberately departing from INV-EC-001's fail-fast, and that departure is
      D-02, not an oversight.
    - Collect the `Cause` of each failing exit (narrow with `Exit.isFailure`, read `.cause`) into a
      local array.
    - If that array is empty, the batch succeeds with `void`.
    - Otherwise fold the collected causes with `Cause.combine` starting from `Cause.empty`, and fail
      with `Effect.failCause(folded)`. Nothing is dropped, nothing wins first, nothing goes to
      `console.warn`.

    Write it as a bare `for` loop of `yield*` inside ONE `Effect.gen`. `Effect.forEach` and
    `Effect.all` are both forbidden here for `ScenarioEffect.ts` note (a)'s reason, restated for this
    module: with a combinator, "every hook runs" becomes "this combinator's default concurrency
    happens to be 1", and adding `{ concurrency: "unbounded" }` reads like a performance win while
    interleaving hooks the author wrote in order.

    Do NOT introduce a wrapper error class. `Cause.combine` preserves each hook's own error value by
    identity inside the combined cause, which is exactly what `ScenarioEffect.ts` note (a) requires
    ("a step's error must reach the Scenario's error channel as the value the step failed with"); a
    `HookFailureError` wrapping them would re-tag and lose that. `Cause.combine(Cause.empty, c)`
    returns `c` unchanged, so a batch with exactly one failure fails with the ORIGINAL cause and the
    existing `Cause.squash(exit.cause)` reference-identity assertion style still works for it. Record
    both facts as a numbered module note naming the plausible tidy-up (wrapping in a named error class
    "to follow the house error style") and the tests that go red.

    Note also, in the same note, that `Effect.ensuring` is NOT the combinator this phase uses anywhere:
    its finalizer's error channel is `never` in `effect@4.0.0-rc.112`, so a hook that can fail is not
    even assignable to it, and it merges no causes. `Effect.onExit` is what plans 07-04 and 07-05 use.
    BEH-EC-006's literal "via `Effect.ensuring`" names the guarantee, not the combinator, and plan
    07-08 corrects the spec text.

    Extend `packages/vitest/test/Hook.test.ts` with, at minimum:
    - an empty batch succeeds.
    - a batch of three hooks where the FIRST fails still runs all three — proven by an append-only
      `Ref` log containing all three names, not merely by the batch failing.
    - a batch with two failures fails with a cause in which BOTH original error values are present by
      reference identity. Walk the cause's reasons (or use `Cause.prettyErrors`/`Cause.fromReasons`
      helpers as available on the installed build) — do NOT use `Cause.squash` for this case, because
      squashing a combined cause does not return either original error by identity.
    - a batch with exactly one failure fails with the original error recoverable by
      `Cause.squash(exit.cause)` reference identity.
    - hooks in a batch run in array order, bracketed `:start`/`:end` around an `Effect.yieldNow` so a
      concurrent implementation is actually falsifiable (`ScenarioEffect.test.ts` L108-127 records
      that a single entry per body let the concurrency mutation survive).

    Add the new mutations to the file's mutation header: (i) `Effect.forEach(hooks, …, { concurrency:
    "unbounded" })` in place of the `for` loop; (ii) `return yield* Effect.failCause(exit.cause)` on
    the first failure (first-wins) in place of the fold.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test author's source → this library | In-process, fully trusted. A hook body is code the developer wrote in their own repo and runs with their own privileges; there is no serialization, no network, no parsing of untrusted input, and no credential handling anywhere in this plan. |
| hook failure value → CI log / reporter | A developer-authored error's message is rendered verbatim by the reporter. This is the only data that leaves the process. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01-01 | Information disclosure | `runHookBatch` combined cause → reporter output | accept | Message content is never truncated or redacted, by the locked developer decision recorded at `packages/gherkin/src/Errors.ts` note (b) and `packages/vitest/src/Errors.ts` note (d). A fixture credential in a hook body's error text will reach a publicly readable CI log; usefulness was chosen over redaction and this plan does not reopen it. |
| T-07-01-02 | Repudiation | a hook failure that is silently dropped | mitigate | `runHookBatch` folds EVERY failing hook's cause into the reported failure (D-03). The acceptance criterion above forbids a first-wins fold, and the two-failure identity test fails if any cause is dropped. |
| T-07-01-03 | Denial of service | a hook body that never completes | accept | A non-terminating hook hangs its test; vitest's own per-test timeout is the control and this package adds none. No new exposure — a non-terminating step body already behaves this way. |
| T-07-01-SC | Tampering | npm/pip/cargo installs | n/a | This plan adds no dependency of any kind. `pnpm-lock.yaml` and both package manifests are unchanged; no package-legitimacy checkpoint applies. |
</threat_model>
