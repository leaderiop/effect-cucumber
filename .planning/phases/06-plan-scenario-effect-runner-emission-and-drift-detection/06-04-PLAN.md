<objective>
Build the Plan stage: join a `ParsedFeature`'s scenarios against a registered step tree, resolve
every Pickle step to exactly one definition, and turn every mismatch into a typed, located,
actionable finding. This is the module that makes MATCH-03, MATCH-04 and MATCH-05 true.

Purpose: ARCHITECTURE.md Pattern 2 makes this a separate pass on purpose — an undefined or
ambiguous step is discovered deterministically for every Scenario BEFORE any test runs, and this
whole module is testable with no vitest machinery at all. It is also the only fan-in point in the
phase: everything downstream (`ScenarioEffect`, `Runner`) consumes fully-resolved value objects,
and per ARCHITECTURE.md's "Internal boundaries" table no matching, scope lookup or Layer decision
may survive past here.

**Matcher construction.** Build ONE `createStepMatcher` per `planFeature` call, over ALL
definitions, with `registry: args.feature.parameterTypes` (verified fact 4) and
`entries: definitions.map((definition) => ({ pattern: definition.pattern, definition }))` — the
opaque `D` payload is the whole `StepDefinition`, which is the slot `StepMatcher.ts:59-61` was
designed for. One matcher, not one per Scenario and not one per scope level: `match()` returns
every match and this module filters, which is both cheaper (the lazy per-registry compilation
cache is hit once per pattern) and the only arrangement in which MATCH-04 can see two competing
patterns at once.

**Scope visibility.** Write a named predicate — `isVisibleTo(definition, scenario, step)` — with
its own doc comment naming ARCHITECTURE.md Pattern 5 and ADR-EC-017. The rule, given that
`RegistryScopeKind` has no `rule` member (verified fact 8):

- `scope.kind === "feature"` → visible to every step of every Scenario.
- `scope.kind === "background"` → visible ONLY to a step whose `origin` is `"feature-background"` or `"rule-background"`. A Background is a step-definition CONTAINER (ADR-EC-017), so its registrations serve Background steps and nothing else.
- `scope.kind === "scenario"` → visible ONLY to a step whose `origin` is `"scenario"` AND whose enclosing `ParsedScenario.astName` equals `scope.name`. Compare against `astName`, never `name`: a Scenario Outline produces one `ParsedScenario` per Examples row, each with a distinct interpolated `name` but the same `astName`, and matching on `name` would make every Outline row's steps resolve to nothing.

**Level precedence.** Rank a visible match: `0` for `background` or `scenario` scope (the inner
level), `1` for `feature` scope. Take the lowest rank that has at least one match and discard the
others — an inner registration SHADOWS an outer one; that is Pattern 5's "first match wins" walking
up the chain, and it is why a Feature-level and a Scenario-level pattern both matching is not an
ambiguity. Two matches at the SAME rank IS the ambiguity (Task 2). Give this its own lettered note
naming the plausible wrong reading — treating any two matches anywhere as ambiguous — and why it
would make a Feature-level default pattern impossible to override.

**Resolution.** For each Scenario in `feature.allScenarios`, for each step in `scenario.steps` in
order: compute the winning group. Exactly one member → a `Resolved` `PlannedStep` carrying
`match.pattern`, `match.definition.body`, and `match.args` (pass `args` through positionally and
UNMODIFIED — a `null` from a non-participating optional group is meaningful and dropping it would
shift every later argument; that is the 03-04 decision). Zero or two-plus → an `Unresolved`
`PlannedStep`, built by Task 2's error builders.
