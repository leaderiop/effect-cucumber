<objective>
Deliver CONTEXT.md D-01's suggested step-definition snippet: given an unmatched step's text and
the `ParameterTypeRegistry` the Feature was parsed with, produce a copy-pasteable
`Given("...", function*(...) {...})` fragment, generalising literal values into
cucumber-expression parameters exactly as cucumber-js does.

Purpose: two reasons this lives in `@effect-cucumber/gherkin` and not in `@effect-cucumber/vitest`,
where 06-PATTERNS.md tentatively placed it. First, it is a hard blocker there:
`packages/vitest/package.json` declares only `@effect-cucumber/gherkin`, and under pnpm's isolated
layout `import ... from "@cucumber/cucumber-expressions"` from `packages/vitest` fails with
`ERR_MODULE_NOT_FOUND` — reproduced during planning, and PITFALLS.md Pitfall 16 is the same defect
that already bit this repo once. Second, every other cucumber-expressions concern in this project
(`ParameterTypes.ts`, `StepMatcher.ts`, `StepPatternMessages.ts`, `StepArgs.ts`) already lives in
the gherkin package; putting the generator there keeps the dependency edge where it is declared
and needs no manifest or lockfile change. The alternatives — re-exporting the third-party
`CucumberExpressionGenerator` class from gherkin's barrel, or declaring the dependency a second
time in `packages/vitest` — either publish upstream surface or create a version pair nothing keeps
in sync.

Output: `packages/gherkin/src/Snippet.ts` and its barrel export.
</objective>

<verified_facts>
Reproduced during planning against the installed `@cucumber/cucumber-expressions@20.1.0`. Do not
re-derive these.

1. `CucumberExpressionGenerator` and `ParameterTypeRegistry` are both exported from the package
   BARREL (`dist/index.d.ts` line 12). Import from `"@cucumber/cucumber-expressions"`, never from
   a deep `dist/` path — the rule stated at `StepMatcher.ts:62-65` and `Model.ts:32-33`.

2. `new CucumberExpressionGenerator(() => registry.parameterTypes)` — the constructor takes a
   THUNK returning an iterable, not the registry. `ParameterTypeRegistry.parameterTypes` is an
   `IterableIterator` getter.

3. `generateExpressions(text)` returns a `readonly GeneratedExpression[]` of length 0 or more,
   MOST SPECIFIC FIRST. Observed outputs against a bare `new ParameterTypeRegistry()`:
   - `"I have 5 apples"` → `[{source: "I have {int} apples", parameterNames: ["int"]}, {source: "I have {float} apples", parameterNames: ["float"]}]`
   - `"the user \"bob\" logs in"` → `[{source: "the user {string} logs in", parameterNames: ["string"]}]`
   - `"nothing special"` → `[{source: "nothing special", parameterNames: []}]`
   - `"I add 3 and 4 apples"` → `[{source: "I add {int} and {int} apples", parameterNames: ["int", "int2"], parameterInfos: [{type:"Number", name:"int", count:1}, {type:"Number", name:"int", count:2}]}]`

4. `parameterNames` ALREADY disambiguates repeats (`int`, `int2`); `parameterInfos[i].name` is the
   undisambiguated parameter TYPE name and is the key to look the TypeScript type up by. Do not
   re-derive disambiguation.

5. `parameterInfos[i].type` is a JS constructor name (`"Number"`, `"String"`) and is NOT a
   reliable TypeScript type source — `{bigdecimal}` produces a `string` and `{biginteger}` a
   `bigint` despite both being numeric-looking. Use the `BuiltInParameterTypeMap`-keyed record
   described in Task 1 instead.
</verified_facts>

Implementation outline. Construct `new CucumberExpressionGenerator(() => args.registry.parameterTypes)`
per call — do not memoise it at module scope, and do not cache it per registry. `Model.ts:206-222`
records that a `ParameterTypeRegistry` is built fresh per `parseFeature` call, and the whole
reason `StepMatcher.ts`'s compilation cache is keyed on the registry INSTANCE is that a cached
object bound to a dead registry silently does the wrong thing; this function runs once per
undefined step, on an error path, so there is no budget worth defending here.

Take `generateExpressions(args.text)` and use element `0` — the most specific candidate, per
verified fact 3. `noUncheckedIndexedAccess` is on, so handle the `undefined` case explicitly
rather than asserting: when the array is empty, fall back to the literal step text as the pattern
with an empty parameter list.

Build the parameter list by zipping `parameterNames[i]` (already disambiguated) with
`parameterInfos[i].name` (the type name). Each parameter renders as
`${name}: ${TS_TYPE_BY_PARAMETER_TYPE_NAME[typeName] ?? "unknown"}`. If a generated name is the
empty string or is not a valid JavaScript identifier, substitute `arg${i + 1}` — the anonymous
`{}` built-in's registry name is the empty string, so this is a reachable case, not defensive
padding.

Render the pattern with `JSON.stringify(source)` so a step text containing a quote, a backslash
or a newline cannot break out of the emitted string literal. `Validate.ts:76-82` sets this
precedent for quoting inside messages; here it is also the injection control named in this plan's
threat model.

The returned string is exactly three lines, with no trailing newline:
`${keyword}(${quotedPattern}, function*(${params}) {`, then a two-space-indented
`// TODO: implement this step` line, then `})`. Keep it as a single template — the caller embeds
it in an error message and adds its own surrounding punctuation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.feature` file text → `generateStepSnippet` | Step text is author-controlled content read off disk and is the direct input to a CODE-SHAPED output string. This is the phase's single highest-value threat surface, named explicitly in the phase brief. |
| custom parameter type registry → the generator | A caller-registered `ParameterType` name reaches the rendered parameter annotation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-02-01 | Tampering / injection | `generateStepSnippet` pattern rendering | mitigate | The pattern is rendered with `JSON.stringify`, so a step text containing `"`, `\`, or a newline cannot terminate the emitted string literal or append trailing code. Task 1's mutation record A is the standing proof that removing this escaping fails a test. |
| T-06-02-02 | Elevation of Privilege | the generated snippet as executable code | accept | The snippet is a STRING embedded in an error message. Nothing in this codebase passes it to `eval`, `new Function`, `child_process`, or a file write, and no such call is added. A developer who copies it into their own source is performing an ordinary, deliberate edit and reviews it as one. `grep -c 'eval(\|new Function' packages/gherkin/src/Snippet.ts` returning 0 is the check. |
| T-06-02-03 | Denial of Service | unbounded step text in the message | accept | `Errors.ts:50-58` is a locked developer decision, pinned byte-for-byte in `packages/gherkin/test/Contracts.test.ts`: message content is never truncated. The input is a `.feature` file the developer wrote and already loaded into memory; a long snippet is a long terminal line, not a resource exhaustion. Truncating here would break the pinned contract. |
| T-06-02-04 | Denial of Service | `generateExpressions` over adversarial text | transfer | Expression generation is `@cucumber/cucumber-expressions@20.1.0`'s own algorithm, pinned by `packages/gherkin/test/expressions-pin.test.ts`. Nothing is hand-rolled here. A pathological input is an upstream concern, and the pin makes an upstream behaviour change visible. |
| T-06-02-05 | Information Disclosure | custom parameter type name in the annotation | accept | A custom name comes from the developer's own `defineParameterType` call and appears only in the developer's own error output. No new disclosure. |
| T-06-02-SC | Tampering | package-manager installs | accept | This plan installs nothing. It deliberately avoids adding `@cucumber/cucumber-expressions` to `packages/vitest`, which is why `pnpm-lock.yaml` must be unchanged — an acceptance criterion asserts `git diff --stat pnpm-lock.yaml` is empty. No new package enters the dependency tree, so there is no `[ASSUMED]`/`[SUS]` package to gate. |
</threat_model>
