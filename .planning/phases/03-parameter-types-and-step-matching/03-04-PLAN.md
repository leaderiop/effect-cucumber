<objective>
Build the matcher. Two properties make it worth writing rather than calling `CucumberExpression`
directly at every call site.

First, **it returns every match.** `@cucumber/cucumber-expressions` does not detect two step patterns
both matching one step text — verified: `I have {int} apples` and `I have {word} apples` both match
`I have 5 apples`, yielding `5` and `"5"` respectively. A matcher that takes the first registration
makes a step argument's TYPE depend on the order the step definitions happened to be written in, and
an unrelated refactor that reorders them silently changes what a test asserts. Returning all matches
is what lets Phase 6 raise MATCH-04's ambiguity error instead of silently picking a winner.

Second, **compilation is memoized per `(registry, pattern)`, never per pattern alone.** A
`CucumberExpression` permanently binds to — and snapshots the parameter types of — the registry it
was constructed with. A cache keyed on the pattern string would serve an expression bound to a stale
registry once the fresh-registry-per-`loadFeature` lifecycle starts producing new registries.

Purpose: MATCH-01 (the runtime half of coercion), roadmap success criteria 1 and 4.
Output: `src/StepMatcher.ts` and `test/StepMatcher.test.ts`.
</objective>

    keyed on the pattern alone is forbidden: an expression snapshots its resolved parameter types at
    construction, so the pattern-only cache silently serves a stale binding as soon as a second
    registry exists.

    Export `compileExpression(registry: ParameterTypeRegistry, pattern: string): CucumberExpression`.
    It returns the cached expression when present, otherwise constructs
    `new CucumberExpression(pattern, registry)` inside a `try`/`catch`, stores it, and returns it.

    On a caught throw, discriminate STRUCTURALLY, never with `instanceof` and never on message text:
    - if the caught value is an object carrying a string property `undefinedParameterTypeName`,
      raise a `StepPatternError` with reason `UndefinedParameterType`, `parameterTypeName` set to
      that property, `pattern` set to the pattern, and a message that names the parameter type, names
      the pattern in full, and tells the caller to define it with `defineParameterType` at module
      scope before any `loadFeature` call runs. Forward the caught value as `cause`. Add a comment
      recording that `UndefinedParameterTypeError` is not exported from the package barrel, which is
      why the check is structural.
    - otherwise raise a `StepPatternError` with reason `InvalidStepPattern`, `pattern` set, the
      upstream message included in full (no truncation), and the caught value as `cause`.

    Export an interface `StepPatternEntry<D>` with readonly `pattern: string` and
    `definition: D`, and an interface `StepMatch<D>` with readonly `pattern: string`,
    `definition: D`, and `args: ReadonlyArray<unknown>`. `D` is an opaque payload the caller owns —

    `effect` still serves Phase 6.

    Export an interface `StepMatcher<D>` with readonly `entries: ReadonlyArray<StepPatternEntry<D>>`
    and readonly `match: (text: string) => ReadonlyArray<StepMatch<D>>`.

    Export
    `createStepMatcher: <D>(args: { registry: ParameterTypeRegistry; entries: ReadonlyArray<StepPatternEntry<D>> }) => StepMatcher<D>`.

    `match(text)` iterates EVERY entry in the order supplied, calls
    `compileExpression(registry, entry.pattern).match(text)`, skips the entry when the result is
    `null`, and otherwise extracts arguments and appends one `StepMatch`. It returns the accumulated
    array — empty for zero matches, length two for two matches.

    `match` MUST NOT throw for a zero-match or a many-match step text, and must not sort, dedupe or
    prefer any entry. Write that as an explicit paragraph in the doc comment: deciding what zero or
    many matches MEANS is ADR-EC-019's job, delivered by MATCH-03 and MATCH-04 in Phase 6, where the
    Scenario and its source location are in hand. A `throw` added here would move a per-Scenario
    failure to a whole-file collection error. Compilation failures are the one exception and DO
    throw, because an invalid pattern is not a matching outcome.

    Argument extraction, per `Argument`:
    - call `argument.getValue(undefined)` inside a `try`/`catch`. On a throw, raise a
      `StepPatternError` with reason `ParameterTransformFailed`, `parameterTypeName` set from
      `argument.getParameterType().name`, `pattern` set, a message quoting the raw matched text from
      `argument.group.value` in full, and the caught value as `cause`. The rationale, worth a
      comment: upstream throws synchronously out of `getValue`, i.e. during extraction and outside
      any Effect, so an unguarded call bypasses the structured error channel entirely.
    - then test the returned value for a thenable — an object or function, not null, whose `then`
      property is a function. If so, raise a `StepPatternError` with reason
      `AsyncParameterTransform`, `parameterTypeName` set, `pattern` set, and a message stating that
      a parameter transform must be synchronous and that async work belongs in the step's Effect
      body. Note in a comment that `ParameterTypeDefinition.transform` already forbids this at the
      type level, so this guard exists for the `any`-cast and plain-JavaScript escape routes.
    - otherwise keep the value as `unknown`. A `null` return from `getValue` (an optional group that
      did not participate) is passed through unchanged, not filtered out — the positional
      correspondence between arguments and the pattern's parameters must be preserved.

    Compilation is LAZY: `createStepMatcher` compiles nothing. The first `match` call compiles every
    entry, because matching has to try them all anyway. That gives fail-fast on an invalid pattern at
    the first match — which under ADR-EC-019 is still Plan time, before any Scenario runs — while
    keeping construction free of the module-evaluation-order coupling Pitfall 13 describes. State
    both halves in the doc comment.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| step text from a `.feature` file → the compiled `CucumberExpression` regex | Feature-file text is developer-authored but reaches a regular expression evaluator on the dev/CI machine |
| step pattern string → `new CucumberExpression` | An invalid pattern must become a named library error rather than a column-numbered upstream throw with no file name |
| a custom transform's return value → the caller's argument array | Arbitrary caller code runs synchronously here; its throws and its Promises both escape unguarded |
| registration order → step semantics | Whether the first or every match is returned decides whether an unrelated refactor can silently change what a test asserts |
