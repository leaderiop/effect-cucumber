<objective>
Prove that ADR-EC-016's `@effect/tsgo` diagnostics are a **build gate**, not
advice. The whole project's core value — "a step needing a service the ambient
Layer doesn't provide is a type error at authoring time" — rests on this
mechanism working. Right now nothing in the repo demonstrates that it does.

This plan builds a small fixture with three probes (two negative, one positive)
and a script that asserts the gate's behavior, so the claim is checkable on
every CI run instead of being assumed.

Purpose: Phase 1 success criterion 2.
Output: `pnpm verify:tsgo-gate`, a one-command proof that a wrong-Layer program
cannot compile.
</objective>

  <action>
The fixture lives under `packages/vitest/` because that is the only package with
`effect` installed. `packages/vitest/tsconfig.json` has `include: ["src"]`, so
`test/tsgo-gate/` is **not** part of the solution build — it gets its own
tsconfigs and is compiled only by the gate script.

Two facts to preserve, both verified empirically against `typescript@7.0.2` +
`@effect/tsgo@0.38.0` in this repo — do not "improve" them away:

- The fixture files must sit under a directory literally named `src` (i.e.
  `test/tsgo-gate/src/`). `@effect/tsgo`'s default per-file override enables
  `floatingEffect` at error severity for paths matching `src/**/*.ts`. Move the
  files out of a `src` segment and the floating-effect probe silently stops
  firing.
- The base plugin block from 01-01 is enough on its own. `missingLayerContext`
  and `floatingEffect` are already error-severity by default. Do **not** add a
  `diagnosticSeverity` map — if the gate needs hand-configuring to fire, the
  proof is weaker.

`src/missing-layer-context.ts` — verified to emit
`error TS377034: Missing 'Dep' in the expected Layer context. effect(missingLayerContext)`:
```ts
import * as Context from "effect/Context"
import * as Effect from "effect/Effect"
import * as Layer from "effect/Layer"

class Dep extends Context.Service<Dep, { readonly n: number }>()("Dep") {}
class Svc extends Context.Service<Svc, { readonly m: number }>()("Svc") {}

const svcLayer = Layer.effect(Svc, Effect.map(Dep, (d) => ({ m: d.n })))

// `svcLayer` is `Layer<Svc, never, Dep>` — `Dep` is unprovided. Annotating it
// as `Layer<Svc>` is exactly the mistake this project must catch at authoring
// time: a Scenario whose ambient Layer does not provide what a step needs.
export const merged: Layer.Layer<Svc> = Layer.merge(svcLayer, Layer.empty)
```

`src/floating-effect.ts` — verified to emit
`error TS377001: This Effect value is neither yielded nor used in an assignment. effect(floatingEffect)`
**with no accompanying plain TypeScript error**. This is the decisive probe: the
file is valid TypeScript, so a non-zero exit can only come from the Effect
diagnostics layer.
```ts
import * as Effect from "effect/Effect"

// Valid TypeScript. Rejected only by @effect/tsgo.
export const run = (): void => {
  Effect.sync(() => 1)
}
```

`src/satisfied.ts` — the positive control. Same shapes, requirements satisfied,
no floating effects. Must compile clean:
```ts
import * as Context from "effect/Context"
import * as Effect from "effect/Effect"
import * as Layer from "effect/Layer"

class Dep extends Context.Service<Dep, { readonly n: number }>()("Dep") {}
class Svc extends Context.Service<Svc, { readonly m: number }>()("Svc") {}

const depLayer = Layer.succeed(Dep, { n: 1 })
const svcLayer = Layer.effect(Svc, Effect.map(Dep, (d) => ({ m: d.n })))

export const merged: Layer.Layer<Svc> = Layer.provide(svcLayer, depLayer)

export const run: Effect.Effect<number, never, Svc> = Effect.map(Svc, (s) => s.m)
```

If `Layer.provide`'s argument order differs in `4.0.0-rc.112`, consult
`packages/vitest/node_modules/effect/dist/Layer.d.ts` and adjust — the
requirement is only that `satisfied.ts` compiles clean, however that is spelled.

Write `scripts/verify-tsgo-gate.sh` (bash, `set -euo pipefail`, made executable
with `chmod +x`). It must make four assertions and fail loudly with a specific
message on each — a silently-passing gate check is worse than none:

1. **Positive control compiles.** `tsc -p .../tsconfig.ok.json` exits 0.
   Failure message: "positive control failed to compile — the gate fixture is
   broken, not the gate."
2. **Negative fixture fails.** `tsc -p .../tsconfig.json` exits non-zero.
   Failure message naming ADR-EC-016: "Effect diagnostics did not fail the
   build — ADR-EC-016's gate is not enforced."
3. **The failure is Effect-caused, by name.** The captured output contains
   `effect(missingLayerContext)`. Failure message: "build failed, but not for
   the Layer-context reason — check whether the diagnostic was renamed or
   downgraded."
4. **A valid-TypeScript-but-invalid-Effect file also fails.** Compile
   `src/floating-effect.ts` on its own (a `tsc --noEmit` invocation on just that
   file, using the fixture tsconfig via `--project` plus a temp `files` config,
   or simply assert the full-fixture output contains `effect(floatingEffect)`
   and that `floating-effect.ts` produces no `TS2` / `TS1` / `TS6` error codes).
   This is what distinguishes "the gate works" from "TypeScript strictness
   happened to catch it."

Use `node node_modules/typescript/bin/tsc` (not a global `tsc`) so the patched
`typescript@7.0.2+effect-tsgo` binary is what runs. Print `✓` lines for each
passing assertion and a final `tsgo gate: ENFORCED` on success.
