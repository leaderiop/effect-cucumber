<objective>
Settle the dependency policy so an Effect rc bump is a one-line diff and a
published tarball cannot strand consumers.

Two traps are being defused at once. First, an exact `effect` pin duplicated
across manifests is easy to bump half-right, and two copies of `effect` in a
consumer's tree silently break `Context` identity — a `Layer` built with one
copy will not satisfy a requirement declared against the other. Second (Pitfall
20), pnpm's `catalog:` protocol expands to its **literal value at pack time**, so
a catalog holding an exact pin publishes an exact *peer* range — exactly how
`@systemfsoftware/effect-gherkin-spec@2.0.0` shipped `effect: "4.0.0-rc.108"`
and broke for rc.109 consumers. The fix is two catalogs: pins for dev, ranges
for peers.

Purpose: Phase 1 success criterion 4's manifest half (the tarball is verified in
plan 01-05). Closes ADR-EC-012 and ADR-EC-015 at the workspace level.
Output: A single bump point for the rc pins, and two publishable manifests.
</objective>

<task type="auto">
  <name>Task 1: Introduce a two-catalog version policy in pnpm-workspace.yaml</name>
  <files>pnpm-workspace.yaml, package.json, packages/gherkin/package.json, packages/vitest/package.json, pnpm-lock.yaml</files>
  <action>
Rewrite `pnpm-workspace.yaml` with a **default catalog holding exact pins**
(consumed by `devDependencies` only) and a **named `peer` catalog holding
ranges** (consumed by `peerDependencies` only):

```yaml
packages:
  - "packages/*"

# Exact pins — devDependencies only. This is the single bump point for an
# Effect rc upgrade.
catalog:
  effect: 4.0.0-rc.112
  "@effect/vitest": 4.0.0-rc.112
  vitest: ^4.1.0
  typescript: ^7.0.2
  "@types/node": ^26.4.0

# Ranges — peerDependencies only. `catalog:` expands verbatim at pack time
# (Pitfall 20), so an exact pin here would publish an exact peer range and
# strand every consumer on a different rc.
catalogs:
  peer:
    effect: ^4.0.0-rc.112
    "@effect/vitest": ^4.0.0-rc.112
    vitest: ">=4.1.0 <5.0.0"
```

The `vitest` peer range is copied verbatim from `@effect/vitest@4.0.0-rc.112`'s
own published manifest. vitest 5 exists as a prerelease and is **not** supported
by `@effect/vitest@4` — do not widen it.

Then rewire the consumers:
- Root `package.json` devDependencies: `typescript` and `vitest` become
  `"catalog:"`.
- `packages/vitest/package.json`: `peerDependencies` for `effect`,
  `@effect/vitest` and `vitest` become `"catalog:peer"`; `devDependencies` for
  the same three become `"catalog:"`.
- `packages/gherkin/package.json`: keep `@cucumber/gherkin`,
  `@cucumber/messages` and `@cucumber/cucumber-expressions` as real
  `dependencies` at their current ranges — they are genuine runtime deps and are
  not in the catalog.

Run `pnpm install` and confirm the named catalog resolves. **Fallback:** if the
installed `pnpm@10.26.1` rejects the `catalogs:` key, drop the named catalog and
write the peer ranges as literals in `packages/vitest/package.json` — the
non-negotiable outcome is that peer ranges are ranges, not that they come from a
catalog. Record any such deviation in the SUMMARY.

Stay on `pnpm@10.26.1` — the phase decision explicitly defers the 11.x bump.
  </action>
  <verify>
```bash

grep -q "catalogs:" pnpm-workspace.yaml && echo "NAMED CATALOG PRESENT"
node -e "const p=require('./packages/vitest/package.json');
  const peer=p.peerDependencies.effect;
  if(/^\d/.test(peer)) { console.error('PITFALL 20: exact peer pin', peer); process.exit(1) }
  console.log('peer range OK:', peer)"
node node_modules/typescript/bin/tsc -b; echo "EXIT=$?"   # EXIT=0
```
  </verify>
  <done>
`pnpm-workspace.yaml` declares both catalogs. `pnpm install` succeeds. The

backed by a range), never a bare exact version. `tsc -b` still exits 0.
  </done>

<task type="auto">
  <name>Task 2: Reshape both package manifests into publishable ESM-only form</name>
  <files>packages/gherkin/package.json, packages/vitest/package.json</files>
  <action>
Both manifests currently use the pre-v4 `main` + `types` + static `dist` exports
shape and are marked `"private": true`. Convert them to the Effect v4 shape
(STACK §4.2). Apply to **both** packages:

- **Remove** `"private": true`, `"main"`, `"types"`. These packages are intended
  for npm; `private: true` blocks the `publishConfig` semantics that criterion 4
  verifies. (Nothing publishes them — there is no release workflow in this
  milestone.)
- `"exports"`: `{ "./package.json": "./package.json", ".": "./src/index.ts" }`
- `"publishConfig"`:
  ```jsonc
  {
    "access": "public",
    "provenance": true,
    "exports": {
      "./package.json": "./package.json",
      ".": "./dist/index.js"
    }
  }
  ```
- `"files": ["src/**/*.ts", "dist"]` — shipping sources alongside `dist`, which
  with `declarationMap` gives consumers go-to-definition into real source.
- `"sideEffects": false`
- `"engines": { "node": ">=20" }`
- `"license": "MIT"`, `"description"`, `"keywords"`,
  `"repository": { "type": "git", "url": "https://github.com/leaderiop/effect-cucumber.git", "directory": "packages/<name>" }`,
  `"homepage"` and `"bugs"` pointing at the same repo.
- Keep `"type": "module"`. Do **not** add a `require` condition or any CJS
  output: `effect@4`, `@effect/vitest@4`, `@cucumber/gherkin@42` and
  `@cucumber/cucumber-expressions@20` are all ESM-only, so a CJS build could not
  `require()` its own dependencies.

Package-specific:
- `@effect-cucumber/gherkin`: **no `effect` entry in any dependency field.**
  ADR-EC-011 scopes it to parsing with no Effect logic; keep it that way so the
  package has no Effect version surface at all.
- `@effect-cucumber/vitest`: `"dependencies": { "@effect-cucumber/gherkin": "workspace:^" }`
  (note `workspace:^`, not `workspace:*` — it expands to a caret range at pack
  time rather than a bare version). All three peers stay required; do not add
  `peerDependenciesMeta.optional` — `@effect/vitest` is not optional for a
  package whose entire purpose is the vitest integration.

**Risk to watch:** pointing dev-time `exports` at `./src/index.ts` while the
packages are composite project references can surface `TS6307`-style errors
("file is not listed within the file list of project"). Run `tsc -b` immediately
after the swap. If it breaks, keep the dev-time `exports` at `./dist/index.js`
and rely solely on `publishConfig.exports` for the published shape — criterion 4
is about the **packed tarball's** manifest, not the source one. Record the
choice in the SUMMARY either way.
  </action>
  <verify>
```bash
pnpm install && node node_modules/typescript/bin/tsc -b; echo "EXIT=$?"   # EXIT=0
for p in gherkin vitest; do
  node -e "const m=require('./packages/$p/package.json');
    if(m.main||m.types||m.private) throw new Error('$p: main/types/private not removed');
    if(!m.publishConfig?.exports?.['.']?.endsWith('dist/index.js')) throw new Error('$p: publishConfig.exports missing');
    if(!m.files) throw new Error('$p: files missing');
    if(m.sideEffects!==false) throw new Error('$p: sideEffects missing');
    console.log('$p manifest OK')"
done
node -e "const g=require('./packages/gherkin/package.json');
  const all={...g.dependencies,...g.devDependencies,...g.peerDependencies};
  if('effect' in all) throw new Error('gherkin must not depend on effect');
  console.log('gherkin has no effect dependency')"
pnpm lint; echo "EXIT=$?"     # EXIT=0 — dprint formats package.json too
```
  </verify>
  <done>
Both manifests are ESM-only, carry `exports` + `publishConfig.exports` + `files`
+ `sideEffects` + `engines`, and declare no `main`/`types`/`private`.
`@effect-cucumber/gherkin` has no `effect` in any dependency field.
`pnpm install`, `tsc -b` and `pnpm lint` all exit 0.
  </done>
