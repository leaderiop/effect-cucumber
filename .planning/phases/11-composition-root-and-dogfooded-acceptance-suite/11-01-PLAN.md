## Assumptions (flagged, from the spec-less edge probe against RUN-06)

No `SPEC.md` exists for this phase, so the deterministic edge probe against RUN-06 surfaced three
edge categories and resolved none of them. They are recorded here as explicit flagged assumptions,
NOT as `must_haves.truths`, so the developer can confirm or overturn each one rather than have it
disappear.

- **ASSUMPTION-11-A (adjacency).** *Probe: "When two things are exactly equal or just touch, do they
  merge, collide, or separate?"* Two acceptance step modules each declare their own
  `Context.Service` whose tag id string is the same literal (for example both using `"World"`). This
  plan ASSUMES they do not collide, because vitest isolates module state per test file and each
  `describeFeature` call provides its own Layer, so no acceptance step ever sees another file's
  service. **Unverified.** If they do collide, the fix is a file-unique tag id per module.
- **ASSUMPTION-11-B (empty / single-element).** *Probe: "What is the result for empty,
  single-element, or null input?"* A structural gate that scans
  `packages/vitest/test/acceptance/*.steps.test.ts` and finds ZERO files passes vacuously, so a
  renamed directory silently disables it. This plan ASSUMES a positive control (a non-zero scanned
  file count plus a known control file that still matches the forbidden pattern) is sufficient, and
  plan 11-05 is where that assumption is exercised. **Unverified here.** Related and also
  unresolved: a Scenario with no cross-step state at all still declares a `World` in this suite by
  convention rather than by necessity.
- **ASSUMPTION-11-C (ordering).** *Probe: "When elements compare equal, is output order specified and
  stable?"* Several acceptance Scenarios assert something about a PRIOR Scenario in the same file (a
  build ordinal, a clock reading that must still be 0). This plan ASSUMES vitest runs one file's
  tests in declaration order, which is what `packages/vitest/test/emission.test.ts` and Phase 10's
  `[1, 1, 1]` assertions already rely on. **Unverified as a stated guarantee** — it is observed
  behavior of the installed runner, not a documented contract, and `--sequence.shuffle` would break
  it. Also unspecified: the row order of `spec/traceability.md` section 5 when two tags map to the
  same `.feature` file. This plan writes them in `REQ-EC-NNN` ascending order.
