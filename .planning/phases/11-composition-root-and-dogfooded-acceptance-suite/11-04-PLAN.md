## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.feature` file text -> `ParsedFeature` -> acceptance step assertions | The step asserts on parser output; a wrong assertion is indistinguishable from a wrong parse unless the fixture is mutated. |
| a module-scope `ParameterTypeStore` -> two `loadFeature` calls -> two registries | A memoised or shared registry is the Pitfall 13 stale-binding class. |
| the acceptance directory glob -> `gherkinTags` and `verify-traceability.sh` | A `.feature` file with no partner step module is new to this directory's conventions. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-11-04-01 | Spoofing | assertions on parser output | high | mitigate | Mutations A, B and C each change the `.feature` file only and require the corresponding Scenario to fail (PROH-11-01). |
| T-11-04-02 | Tampering | the module-scope custom parameter type store | medium | mitigate | The store is created with `createParameterTypeStore()` and never `defaultParameterTypeStore`, which is append-only for the life of the process; asserted by a `grep -c 'defaultParameterTypeStore'` of 0. |
| T-11-04-03 | Tampering | registry freshness across two loads | high | mitigate | A reference-INEQUALITY assertion between the two `parameterTypes` values, with mutation E proving the two-loads-succeeded assertion alone stays green without it. |
| T-11-04-04 | Denial of service | a tagless `.feature` in the acceptance directory | low | accept | Recorded as ASSUMPTION-11-B with a required observation and a documented fallback (move it under a `support/` subdirectory). Accepted because the observable blast radius is this one directory. |
