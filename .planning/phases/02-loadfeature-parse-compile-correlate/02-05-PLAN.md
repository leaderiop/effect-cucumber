<objective>
Build `Correlate.ts`: one AST walk that produces four outputs, one index built from the pickle
array, and the join that turns them into a `ParsedFeatureCore`. This is ADR-EC-014's core and it
is PARSE-02.

The AST walk exists for exactly one reason: to recover what pickles structurally cannot carry —
step keyword, step origin, step line, Rule membership, un-interpolated scenario names, and
Examples column names. Everything a pickle DOES carry (substituted text, flattened tags, stacked
Background steps, per-row location) is read from the pickle. Re-deriving any of those is
forbidden by ADR-EC-014.

Purpose: this is the contract Phase 5 and Phase 6 consume across the package boundary.
Output: `src/Correlate.ts` and the F21 row-by-row test.
</objective>

    For each `AstScenarioInfo` in document order, look up its pickles in `byScenarioId` (missing
    key yields an empty array — that is a legal state that `Validate.ts` turns into
    `EmptyExamples`, so `correlateFeature` must NOT throw for it). For each pickle produce a
    `ParsedScenario` with:
    - `id` from `pickle.id`, `astId` from the AST node id
    - `name` from `pickle.name` (interpolated), `astName` from the AST node's own name
      (un-interpolated). Both are required — this is success criterion 4.
    - `keyword` from the AST node's trimmed keyword
    - `tags` from `pickle.tags` mapped to their `name` strings, in the order `compile()` produced
      them. Do NOT sort, deduplicate, or recompute from the AST.
    - `steps` by mapping `pickle.steps` IN ORDER through a per-step resolver
    - `location` from `pickle.location` — per-Examples-row precise for an Outline. Do NOT look up
      `astNodeIds.at(-1)` in a row-id map; that index is dead code.
    - `ruleId` from the AST node's enclosing rule
    - `pickle` retained as the raw escape hatch

    The per-step resolver takes a `PickleStep` and the `byStepId` index. It reads
    `ps.astNodeIds[0]` (again `string | undefined` under `noUncheckedIndexedAccess`) and looks up
    the `AstStepInfo`. If the lookup misses, throw a `LoadFeatureError` with
    `reason: "ParseFailed"` whose message quotes the step text and the unresolved node id — a
    pickle step referencing an AST node that does not exist means the two halves of the pipeline
    disagree, which must never be silent. The resolved `ParsedStep` takes:
    - `id` from `ps.id`
    - `text` from `ps.text` — already interpolated, with the Background-under-Outline exception
      that `Validate.ts` catches
    - `keyword` from `info.step.keyword.trim()` — the raw AST keyword carries a TRAILING SPACE
    - `keywordType` from `info.step.keywordType` — the AST value, which has a `Conjunction`
      member. Do NOT use `ps.type`: verified, `PickleStep.type` has no `Conjunction`, so an
      `And b` after `Given a` reports `Context` and a `But d` after `When c` reports `Action`.
    - `origin` from `info.owner`
    - `line` from `info.step.location.line` — `PickleStep` carries no location at all
    - `argument` from `ps.argument`, passed through RAW and unwrapped. Phase 4 owns the
      `DataTable` wrapper; wrapping it here creates a merge conflict for no benefit.

    Assemble `ParsedFeatureCore`: `uri` from the caller (never from `document.uri`, which is
    `undefined` when parsing from a string), `name`/`keyword`/`description`/`location` from
    `document.feature`, `language` from `document.feature.language`, `tags` from the feature's own
    AST tag names, `scenarios` holding only feature-level scenarios, `rules` holding each
    `ParsedRule` with its own scenarios, `allScenarios` holding every scenario flat in document
    order, plus `document` and `pickles`.

    `correlateFeature` performs NO validation. Every silent-wrong case is detected in
    `Validate.ts`, over the correlated result. That separation is what lets a failing fixture tell
    you whether correlation or validation broke; inlining checks here destroys that signal.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pickle `astNodeIds` → AST index lookup | Ids from `compile()` are looked up in maps built from the AST; a mismatch means the two halves of the pipeline disagree |
| `document.feature.language` → `dialects[language]` | A language string from file content indexes a package-provided record |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Denial of Service | ReDoS via a feature-derived `RegExp` | mitigate | `Correlate.ts` constructs no `RegExp` at all; keyword matching uses `Array.includes` against the package-provided `dialects` record. Asserted by an acceptance criterion (`new RegExp` count is 0). |
| T-02-12 | Tampering | `dialects[language]` lookup on attacker-influenced content | mitigate | `noUncheckedIndexedAccess` makes the result `Dialect \| undefined`; the code narrows explicitly and returns `false` for an unknown language rather than throwing or reading a prototype property. An unknown `# language:` header has already been rejected as `UnknownDialect` in `Parser.ts` before this point. |
| T-02-13 | Spoofing | an unresolvable `astNodeIds[0]` silently producing a wrong step | mitigate | A missed `byStepId` lookup throws `LoadFeatureError` with `reason: "ParseFailed"` naming the step text and the unresolved id, rather than falling back to a default keyword or origin. |
| T-02-02 | Information Disclosure | step text quoted in the unresolved-node error | accept | Per the locked full-content policy, the step text is quoted verbatim. |
</threat_model>
