<objective>
Close the one claim no in-process test can make: that a tag actually landed on the real task object,
observable through the runner's own CLI filtering and its own reporter.

Purpose: roadmap criterion 4's first half ("a tag filter selects exactly the tagged Scenarios") and
criterion 2's reporter half ("the test is REPORTED skipped") are only visible from outside the
process. RESEARCH Finding 7 verified that a CLI filter marks non-matching tests SKIPPED rather than
removing them, while D-03's `excludeTags` removes them entirely — two different reporter footprints,
neither able to masquerade as the other. This gate asserts both.
Output: one new gate script, a root npm script, a CI step.
</objective>

<!-- Verified CLI semantics (RESEARCH Finding 7, executed against vitest 4.1.11):

     A CLI tag filter sets non-matching tests to skip mode; it never removes them. Filtering runs
     LAST inside the runner's mode interpretation and only ever narrows to skip, so it can never
     un-skip a @skip test. A filtered pattern must itself be declared in the config's tag list,
     regardless of the strict-tags setting (Finding 2).

     Consequently:
       - a Scenario removed by excludeTags   → ABSENT from the report
       - a Scenario narrowed out by a filter → PRESENT, reported skipped
       - a Scenario tagged @skip             → PRESENT, reported skipped

Preconditions, before any run:
- `packages/vitest/test/emission.test.ts` exists.
- Each of the four titles is found in that file by `grep -F`. A rename must fail this gate by name
  rather than turning a later assertion silently vacuous — this is the gate's positive control for
  its own target, in the same role assertion 1 plays in `verify-no-runner-dep.sh`.
- `vitest.config.ts` exists and declares `@only`.

Use the runner's machine-readable reporter and parse the output with `node -e` rather than grepping
for reporter glyphs. Glyph output varies with TTY, colour and reporter settings; the structured
result does not. Write a helper that runs one invocation, writes the report to a temp file, and
exposes a small `node -e` query returning a test's status by its title.

Run A — unfiltered, that file only. Assert:
1. VACUITY CONTROL: the report contains a non-zero number of results. Zero means the file failed to
   collect (which is what an undeclared tag does), and every later assertion would then be vacuous.
   Fail with a message saying so.
2. The `@only`-tagged Scenario is PASSED. This is criterion 3 observed from outside the process:
   the runner is invoked with the CI-mode only-policy this repo's config sets, and a real
   only-modifier would fail here.
3. The `@skip`-tagged Scenario is SKIPPED — criterion 2's reporter half, which no in-process
   assertion can make.
4. The excluded `@wip` Scenario title is ABSENT from the results entirely — not skipped, absent.
   This is D-03, and it is the assertion that distinguishes a registration filter from every other
   mechanism.

Run B — the same file with the runner's CLI tag filter set to the `@only` tag. Assert:
5. VACUITY CONTROL: at least one test PASSED. A filter that matched nothing would otherwise make
   assertion 6 trivially true.
6. The `@only`-tagged Scenario is PASSED — the filter selected it, which is only possible if the
   library put that exact tag string on the real task.
7. The untagged Scenario is SKIPPED and still PRESENT in the results. RESEARCH Finding 7: a CLI
   filter narrows to skip and never removes. Together with assertion 4, this is the pair that proves
   the two mechanisms are distinguishable and that neither is masquerading as the other — say so in
   the script's METHOD NOTE.

Carry a METHOD NOTE in `verify-no-runner-dep.sh`'s voice, stating what `pnpm test` exiting 0 does NOT
prove: the suite passing says nothing about whether a tag reached the real task, because the library
could drop every tag and every in-process assertion would still be green. Only an invocation that
FILTERS on the tag can tell the difference, and that is what this script is.
