put the supersession in the title as ADR-EC-021 does.

Its Context must state the two things that forced a new decision, both of them empirical rather than
preferential:
- The runner's strict-tags setting defaults to ON, so emitting any tag with no declaration fails the
  ENTIRE test file with zero tests collected — and a CLI tag filter validates its pattern against the
  declared tags regardless of that setting. ADR-EC-020's central promise, that running one Scenario
  locally is a bare `--tagsFilter '@only'` choice, therefore did not work for any consumer. Cite the
  research as the source and state that it was verified by execution, not read.
- The user deliberately extended the scope: a library-level registration filter was chosen over
  CLI-only filtering.

Its Decision must state, each as its own bullet:
1. Every tag on a Scenario, inherited ones included, is emitted as a native tag on the generated test,
   with its literal `@` prefix retained and no normalisation.
2. `@skip` additionally emits the test as skipped, which means its body is never invoked and therefore
   neither its steps nor any of its hooks run — a structural property, not an arrangement.
3. `@only` is never routed to the runner's only-mode. It is a plain tag. This is what makes a
   committed `@only` unable to fail a CI run.
4. `includeTags` and `excludeTags` on `describeFeature`'s fourth argument filter at REGISTRATION time:
   an excluded Scenario never becomes a test and is ABSENT from the report, as distinct from a CLI
   filter, which reports non-matching tests as skipped. Both mechanisms compose; neither replaces the
   other. Syntax is a plain array of tag strings, not the runner's boolean expression grammar.
   `undefined` and `[]` both mean no filter.
5. The tag universe must be declared in the runner's config. The library does not fail a Feature over
   an undeclared tag: it catches the rejection, re-emits the test untagged, and prints a warning
   naming the file, the Scenario and the tag — so the Scenario runs but a CLI filter cannot select
   it. `gherkinTags("features/**/*.feature")` is the supported way to generate those declarations from
   a consumer's own `.feature` files.
6. Record `gherkinTags`' shape: it accepts a GLOB PATTERN, or an array of patterns, resolved against
   `process.cwd()` — the shape this phase originally scoped. It is implemented with `tinyglobby`'s
   `globSync`, which makes `tinyglobby` the vitest package's one non-workspace runtime dependency, and
   `globSync` specifically because a runner config is evaluated synchronously at load time — the same
   constraint that rules out reusing the gherkin package's Effect-returning file reader, whose
   synchronous execution throws. Name the two rejected alternatives with their reasons: the platform's
   own `fs.globSync` requires Node 22 while this package declares `>=20`, and a hand-written matcher
   would mishandle character classes and brace expansion. State that the dependency was a deliberate
   choice rather than an incidental one.

Its Consequences must state, under Negative or Trade-off accepted: a consumer with no tag declarations
gets working tests with unfilterable tags plus a warning per affected Scenario; the vitest package now
ships a third-party runtime dependency where it previously had only its workspace sibling, so a
consumer's install graph grows by one small, single-purpose package; and the `AfterAllScenarios`
carve-out (Task 2) is a real behaviour change for a fully-skipped or fully-filtered Feature.

Then add a one-line status banner to `spec/decisions/020-vitest-native-tags-for-skip-only.md` naming
ADR-EC-026, following ADR-EC-015's form. Do NOT rewrite ADR-EC-020's body — ADR-EC-014's precedent is
to mark in place so the superseded reasoning stays readable. State in the banner precisely which parts
no longer hold (the CLI-only filtering clause and the unconfirmed config-time mechanics) and which
still do (native tag emission, `@skip` to skip, `@only` never to only-mode).

Append the ADR-EC-026 triple to `spec/decisions/index.yaml`.
