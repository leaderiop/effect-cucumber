Create `packages/vitest/src/GherkinTags.ts` exporting exactly the surface in the `<interfaces>` block.

**Signature decision to implement and to record in the module doc comment.** The parameter is an
explicit `ReadonlyArray<string>` of paths — each entry is either a `.feature` FILE or a DIRECTORY
scanned recursively for `.feature` files — and NOT a glob pattern. Record the reasoning as a
deliberate, documented deviation from the phase's D-09 wording, with the three facts that forced it:
`fs.globSync` needs Node 22 and this package declares `>=20`; adding a glob package would make a
published runtime dependency out of a config-time convenience and would need its own dependency
audit; and hand-writing a partial glob matcher would silently mishandle character classes and braces.
An explicit path list is also the stronger form of the security control the phase already requires —
the caller names every directory, and there is no pattern for a `**` to expand out of a project.

Implementation, using `node:fs` only (submodule namespace import style: `import * as fs from "node:fs"`
and `import * as path from "node:path"`):
- The parameter is REQUIRED and has no default. Throw a plain `Error` naming `gherkinTags` when it is
  empty — a helper that scans nothing returns nothing, and a config declaring nothing makes every tag
  in the suite undeclared. Silence here is the failure mode, not a convenience.
- For each entry: `fs.statSync` it. A path that does not exist throws a plain `Error` naming the path
  and `gherkinTags`, in `planFor`'s style — a mistyped root that returned `[]` would make an entire
  suite's tags undeclared with nothing saying why. A file entry is used directly; a directory entry is
  walked with `fs.readdirSync(dir, { recursive: true, withFileTypes: true })` and filtered to entries
  whose name ends in `.feature`. Node's recursive `readdirSync` does not follow symlinked directories;
  state that as the traversal-safety property rather than leaving it implicit.
- Read each file with `fs.readFileSync(file, "utf8")`.
- Extract tags line by line: a Gherkin tag line is a line whose TRIMMED form begins with `@`; collect
  every whitespace-delimited token on it that begins with `@`. Track DocString fences — toggle a
  skip flag on a line whose trimmed form starts with three double-quotes or three backticks — so a
  `@`-leading line inside a DocString is not mistaken for a tag line.
- De-duplicate and sort the result ascending, so a config's declared list is stable across runs and
  across filesystem ordering.

Write the trade-off into the module doc comment, in this package's lettered "N things not visible from
the code" format: this is a TEXT SCAN, not a parse. It cannot distinguish which Scenario a tag lands
on and it does not run the Gherkin compiler — but it does not need to, because the only question the
runner config asks is which tag NAMES exist in the suite. The error direction matters and must be
stated: over-declaring a tag costs nothing, while under-declaring one fails a whole test file, so the
scan is deliberately inclusive.

Also state in the doc comment: this module is a leaf with no local imports; it is CONSUMER-FACING and
is exported from the barrel by this same plan (unlike every other module in this package, which is
internal); and it is called from a runner config at load time, which is why it is synchronous and why
it cannot reuse the sibling package's Effect-returning file reader.
