# Traceability Matrix

## Traceability chain

```
Behavior (BEH-EC-NNN)
    → Source module (packages/*/src/*.ts)      [both: built]
    → Test file (packages/*/test/*.test.ts)     [both: built]
    → Invariant (INV-EC-NNN)
    → Decision (ADR-EC-NNN)
    → Acceptance scenario (REQ-EC-NNN)          [real — §5, packages/vitest/test/acceptance/]
```

Sections §1–§6 are parsed by `spec/scripts/verify-traceability.sh`; column
order is a contract. The verify script checks that every ID is traced here, not
that a named file exists, so nothing automated would catch the **Source module**
column naming a module that does not exist — which is why this preamble tracks
that column by hand. As of Phase 10 every module it names is real; the paragraph
below records the ones that were once listed as planned and why none of them was
ever built.

`packages/gherkin/src` and `packages/gherkin/test` are entirely real.
`packages/vitest/src` now has real source too — `describeFeature.ts`, `Dsl.ts`,
`Step.ts`, `Registry.ts`, `CallSite.ts`, `Errors.ts`, `TestApi.ts`, `Plan.ts`,
`ScenarioEffect.ts`, `Runner.ts`, `Hook.ts`, `HookRegistry.ts`,
`OutlineTitle.ts`, `ScenarioKey.ts`, `Tags.ts`, `GherkinTags.ts` and the
`index.ts`
barrel — and `packages/vitest/test` has real suites. This document now names NO
planned module under `packages/vitest`: the last one it did, `SharedLayer.ts`
(Phase 10), was never built and never will be, for the same reason `Rule.ts` and
`ScenarioOutline.ts` were not (below). A shared Layer is a PROVISION STRATEGY,
not a stage — it is one branch in `describeFeature.ts`'s composition root, a
second `TestApi` constructed over the `it` that `@effect/vitest`'s `layer(...)`
hands back, and a `sharedLayer` field on `FeatureCollection` — so a dedicated
module would have had nothing to own, and putting one there would have meant a
second module importing a test framework, which
`scripts/verify-testapi-seam.sh` exists to forbid. `Tags.ts` was in that planned
list until Phase 9 and is now real — it holds the reserved `@skip`/`@only` constants and
the registration-time tag filter, and it is INTERNAL rather than re-exported
from `packages/vitest/src/index.ts`. `GherkinTags.ts` was never on that list at
all: it is new public surface added by Phase 9 (ADR-EC-026's D-09), and unlike
every other module named here it IS exported from the barrel, because it is
called from a consumer's own runner config rather than from inside the
register → plan → emit pipeline.
Background has no separate module on disk, and never will: its steps are
inlined as the leading `yield*`s of the same Effect a Scenario's own steps run
in (ADR-EC-004), so there is nothing left for a dedicated module to build.
`Rule.ts` and `ScenarioOutline.ts` were listed here as planned until Phase 8,
and are now in the same category as Background rather than the same category as
`Tags.ts`: neither was built, and neither will be. A Rule is a registration
SCOPE, not a stage — it is a `ruleId` on `RegistryScope`, an arm of `Plan.ts`'s
`isVisibleTo`, a container on `Dsl.ts`'s `FeatureDsl`, and a `Layer.provideMerge`
in `describeFeature.ts`, so a dedicated module would have had nothing to own. A
Scenario Outline is not a container the author declares at all: its rows arrive
already interpolated as ordinary Pickles (ADR-EC-014), so the only Outline-shaped
thing left to build was the row title format, which is `OutlineTitle.ts`.
`Plan.ts`, `ScenarioEffect.ts` and `Runner.ts` are all reachable from a
user-facing call: `describeFeature` plans its collection, writes any unused-pattern
warnings to the terminal, and emits the result, so `planFeature`,
`buildScenarioEffect` and `emitFeature` each run on the path a test author
actually takes. `packages/vitest/test/emission.test.ts` is the end-to-end
assertion of that, and the only file in the repo that calls `describeFeature` for
real.
§4's rows name only real files. See `spec/roadmap.md` for
what's actually built.

## §4 Test file map

Every row below names a real file on disk. The preamble's planned/real split
applies to the **Source module** column above, never to this section.

The rows below are enumerated from disk — one per `packages/gherkin/test/*.test.ts` and
`packages/vitest/test/*.test.ts` file — plus **three deliberate non-suite entries**,
`packages/gherkin/test/StepArgs.types.ts`, `packages/vitest/test/GherkinTags.types.ts` and
`packages/vitest/test/SharedLayerConstraint.types.ts`. All three are
compiled by `pnpm typecheck:test` and none is ever collected by vitest (their `.types.ts` suffix
is outside the vitest include glob, which is the point of the suffix). Each is listed here because
it is the ONLY place its claim is asserted: `StepArgs.types.ts` carries MATCH-01's type-level
claim — that `{int}`/`{float}` are `number` and `{string}`/`{word}` are `string` — and, since
Phase 11, BEH-EC-016's step-body-signature claim that a DataTable is NOT inferred from the pattern
and must be hand-annotated, which is a claim about what a type deliberately does not do and so has
no runtime surface at all;
`GherkinTags.types.ts` carries RUN-05's config-compatibility claim, that `gherkinTags`' result
spreads into the runner's own `TestTagDefinition[]`, which every runtime assertion about the helper
(all of them about strings) is structurally unable to check, and
`SharedLayerConstraint.types.ts` carries RUN-03's D-04 constraint, that a `shared` Layer whose error
channel is not `never` fails to compile while `perScenario`'s stays unconstrained — a claim about
what does NOT compile, which no running test can make. None is a stray file to be "fixed"
by renaming it to `.test.ts`, which would break `pnpm test` with "No test suite found".

## §5 Acceptance scenario traceability

The rows below are enumerated from the tagged `.feature` files under
`packages/vitest/test/acceptance/`, which is the **only** directory in the
repository where a `.feature` file may carry a `@REQ-EC-NNN` tag. The `.feature`
files under `packages/gherkin/test/fixtures/` and
`packages/vitest/test/fixtures/` are parser and tag-scanning fixtures, and
`packages/gherkin/test/fixtures/README.md` states the prohibition for its own
corpus explicitly. `spec/scripts/verify-traceability.sh` check 4 enforces both
halves: it greps every `.feature` file in the repository for the tag pattern and
fails `pnpm verify:spec` naming any tag that has no row here.

The ids are allocated 1:1 against `.planning/REQUIREMENTS.md`'s 22 v1
requirements, in the order written there, per
`spec/process/requirement-id-scheme.md`'s "allocated contiguously, in the order
written" rule. They are permanent: never renumbered and never reused
(AGENTS.md §6).

**Not all 22 are carried yet, and this list says which.** Six remain:
`REQ-EC-003`, `REQ-EC-007`, `REQ-EC-008`, `REQ-EC-009`, `REQ-EC-016` and
`REQ-EC-018` are ALLOCATED but their
fixtures have not landed; only the rows in the table below name a `.feature`
file that exists on disk today. Two structural facts about the remaining
allocation are worth stating before the fixtures arrive, because neither is
visible from a row:

- Five of them — `REQ-EC-003` (PARSE-03), `REQ-EC-007` (MATCH-03),
  `REQ-EC-008` (MATCH-04), `REQ-EC-009` (MATCH-05) and `REQ-EC-018` (RUN-02) —
  cover "fails loudly" behaviors. A Scenario demonstrating one of those directly
  would be a RED test, so the tag will sit on a deliberately-failing fixture that
  is never emitted as a test, and a wrapper test will drive the fixture and
  assert the specific named error. The wrapper is what passes. This mirrors
  `scripts/verify-tsgo-gate.sh`'s satisfied/starved fixture pair, one level up:
  a runtime error instead of a compile diagnostic.
- Several rows that HAVE landed carry only half their requirement, and each says
  so in its **Verified by** column rather than leaving the gap implied. Two
  shapes recur. A claim about what does NOT compile — `REQ-EC-010`,
  `REQ-EC-012`, `REQ-EC-014` and `REQ-EC-019` — is carried by
  `scripts/verify-tsgo-gate.sh` or a `.types.ts` pin, because no running test can
  state it. A claim about ABSENCE, or about a value only the type system holds,
  is the same problem from a different direction: `REQ-EC-001`'s "contributes
  zero tests" is carried by `scripts/verify-no-runner-dep.sh`, `REQ-EC-005`'s
  compile-time coercion by `packages/gherkin/test/StepArgs.types.ts`,
  `REQ-EC-006`'s definition-time rejections by the two parameter-type test files,
  and `REQ-EC-017`'s fail-fast half by
  `packages/vitest/test/ScenarioEffect.test.ts`. A row whose Scenario is the
  whole of its claim names no second artifact.

One more structural fact, stated here because it applies to every row and to
none of them visibly. A row's Scenario passing is not by itself evidence that
the row's `@REQ-EC-NNN` tag reached the runner. Measured in plan 11-01:
`describeFeature.ts`'s D-08 catch-and-degrade intercepts an undeclared tag at
collection time and re-emits the Scenario UNTAGGED behind one located warning,
so `pnpm test` still exits 0 and the Scenario still passes with its tag
invisible to the runner. What breaks in that state is `--tagsFilter`, which
`scripts/verify-tags-filter.sh` is what exercises. The rows below therefore
claim what their Scenario BODIES assert, and name a separate artifact wherever
the claim is about the tag itself.
