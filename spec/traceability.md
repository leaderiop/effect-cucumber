# Traceability Matrix

## Traceability chain

```
Behavior (BEH-EC-NNN)
    → Source module (packages/*/src/*.ts)      [both: built]
    → Test file (packages/*/test/*.test.ts)     [both: built]
    → Invariant (INV-EC-NNN)
    → Decision (ADR-EC-NNN)
    → Acceptance scenario (REQ-EC-NNN)          [real — §5, packages/vitest/test/acceptance/]
```

Sections §1–§6 are parsed by `spec/scripts/verify-traceability.sh`; column
order is a contract. The verify script checks that every ID is traced here, not
that a named file exists, so nothing automated would catch the **Source module**
column naming a module that does not exist — which is why this preamble tracks
that column by hand. As of Phase 10 every module it names is real; the paragraph
below records the ones that were once listed as planned and why none of them was
ever built.

`packages/gherkin/src` and `packages/gherkin/test` are entirely real.
`packages/vitest/src` now has real source too — `describeFeature.ts`, `Dsl.ts`,
`Step.ts`, `Registry.ts`, `CallSite.ts`, `Errors.ts`, `TestApi.ts`, `Plan.ts`,
`ScenarioEffect.ts`, `Runner.ts`, `Hook.ts`, `HookRegistry.ts`, `HookTagExpression.ts`,
`OutlineTitle.ts`, `ScenarioKey.ts`, `Tags.ts`, `GherkinTags.ts` and the
`index.ts`
barrel — and `packages/vitest/test` has real suites. This document now names NO
planned module under `packages/vitest`: the last one it did, `SharedLayer.ts`
(Phase 10), was never built and never will be, for the same reason `Rule.ts` and
`ScenarioOutline.ts` were not (below). A shared Layer is a PROVISION STRATEGY,
not a stage — it is one branch in `describeFeature.ts`'s composition root, a
second `TestApi` constructed over the `it` that `@effect/vitest`'s `layer(...)`
hands back, and a `sharedLayer` field on `FeatureCollection` — so a dedicated
module would have had nothing to own, and putting one there would have meant a
second module importing a test framework, which
`scripts/verify-testapi-seam.sh` exists to forbid. `Tags.ts` was in that planned
list until Phase 9 and is now real — it holds the reserved `@skip`/`@only` constants and
the registration-time tag filter, and it is INTERNAL rather than re-exported
from `packages/vitest/src/index.ts`. `GherkinTags.ts` was never on that list at
all: it is new public surface added by Phase 9 (ADR-EC-026's D-09), and unlike
every other module named here it IS exported from the barrel, because it is
called from a consumer's own runner config rather than from inside the
register → plan → emit pipeline.
Background has no separate module on disk, and never will: its steps are
inlined as the leading `yield*`s of the same Effect a Scenario's own steps run
in (ADR-EC-004), so there is nothing left for a dedicated module to build.
`Rule.ts` and `ScenarioOutline.ts` were listed here as planned until Phase 8,
and are now in the same category as Background rather than the same category as
`Tags.ts`: neither was built, and neither will be. A Rule is a registration
SCOPE, not a stage — it is a `ruleId` on `RegistryScope`, an arm of `Plan.ts`'s
`isVisibleTo`, a container on `Dsl.ts`'s `FeatureDsl`, and a `Layer.provideMerge`
in `describeFeature.ts`, so a dedicated module would have had nothing to own. A
Scenario Outline is not a container the author declares at all: its rows arrive
already interpolated as ordinary Pickles (ADR-EC-014), so the only Outline-shaped
thing left to build was the row title format, which is `OutlineTitle.ts`.
`Plan.ts`, `ScenarioEffect.ts` and `Runner.ts` are all reachable from a
user-facing call: `describeFeature` plans its collection, writes any unused-pattern
warnings to the terminal, and emits the result, so `planFeature`,
`buildScenarioEffect` and `emitFeature` each run on the path a test author
actually takes. `packages/vitest/test/emission.test.ts` is the end-to-end
assertion of that, and the only file in the repo that calls `describeFeature` for
real.
§4's rows name only real files. See `spec/roadmap.md` for
what's actually built.

## §2 Invariant traceability

INV-EC-001, INV-EC-002, INV-EC-003, INV-EC-004 and INV-EC-005 are enforced
today, by the
assertions their **Test** columns name. INV-EC-002's row covers BOTH Layer scopes
as of Phase 10: the per-Scenario tier's freshness on the default path, and — on
the `shared` path — the same tier still rebuilt per Scenario beside a shared tier
that deliberately is not, which is why its **Test** column names a gate script
alongside its suites. INV-EC-005 joined them in Phase 8, and is the only invariant enforced on BOTH
sides at once — a runtime half (a Rule-scoped registration cannot resolve
another Rule's step) and a compile-time half (a Rule-scoped service is not in
scope outside its Rule), which is why its **Test** column names both a suite and
a gate script. INV-EC-006 joined them in Phase 11 and was the last to do so:
every row in this table now names a real mechanism, and every **Test** column
names a runnable artifact rather than a placeholder. Its enforcement is
deliberately SCOPED and its row says so — a structural scan over the acceptance
suite, which is the code in this repository that plays the consumer's part, and
not over a consumer's own step modules. **LINT-01**,
`scripts/templates/verify-consumer-ref-state.sh`, ships the same scan
generalized into a template a consumer copies into their own repository and
runs in their own CI — this package does not run it against a consumer's tree
automatically, so a consumer who has not adopted it is still governed by
convention, and this table claims nothing else. INV-EC-007 joined afterward,
over `Runner.ts`'s `Random.withSeed` wrap, and is enforced end to end from the
start — no scoped or deferred half. INV-EC-008 and INV-EC-009 joined next, over
`VitestTestApi.ts`'s `Effect.Metric` wrapper and `RerunKey.ts`'s
`rerunKeysForPlan` respectively, both enforced end to end from the start too. INV-EC-010 joined most recently, over `RuleNarrowing.ts`'s `narrowRuleDsl`, and is
enforced on both sides at once — a compile-time half (`scripts/verify-tsgo-gate.sh` assertions
15–16) and a run-time half — the same shape INV-EC-005 already has.

## §4 Test file map

Every row below names a real file on disk. The preamble's planned/real split
applies to the **Source module** column above, never to this section.

The rows below are enumerated from disk, from **three** globs and not two:
`packages/gherkin/test/*.test.ts`, `packages/vitest/test/*.test.ts` and
`packages/vitest/test/acceptance/**/*.test.ts`. The third joined in Phase 11 and
is the reason this sentence now names them individually: the acceptance suite is
one directory DEEPER than the other two, so the single-star globs that had served
since Phase 3 do not reach it, and seven files would have sat on disk untraced
with nothing going red. That third glob is written with `**` deliberately — the
`negative/` subdirectory is a level deeper again, and `negative-requirements.test.ts`
is the file that redeems its fixtures.

Two things under that third glob are deliberately NOT rows here, and neither
absence is drift. The acceptance `.feature` files and the starved fixtures under
`packages/vitest/test/acceptance/negative/` are traced by **§5** instead, one row
per `@REQ-EC-NNN` tag, which is a finer-grained mapping than this table's
one-row-per-suite shape can express — the same division of labour
`packages/vitest/test/tsgo-gate/` already has with `scripts/verify-tsgo-gate.sh`
(see the note below this table). A `.feature` file is not a test module: vitest
collects neither, and listing them here would put the same artifact in two tables
with two different claims attached.

Beyond the three globs, the table carries **five deliberate non-suite entries**,
`packages/gherkin/test/StepArgs.types.ts`, `packages/vitest/test/GherkinTags.types.ts`,
`packages/vitest/test/SharedLayerConstraint.types.ts`, `packages/vitest/test/HookRegistrar.types.ts`
and `packages/vitest/test/Attachments.types.ts`.
All five are
compiled by `pnpm typecheck:test` and none is ever collected by vitest (their `.types.ts` suffix
is outside the vitest include glob, which is the point of the suffix). Each is listed here because
it is the ONLY place its claim is asserted: `StepArgs.types.ts` carries MATCH-01's type-level
claim — that `{int}`/`{float}` are `number` and `{string}`/`{word}` are `string` — and, since
Phase 11, BEH-EC-016's step-body-signature claim that a DataTable is NOT inferred from the pattern
and must be hand-annotated, which is a claim about what a type deliberately does not do and so has
no runtime surface at all;
`GherkinTags.types.ts` carries RUN-05's config-compatibility claim, that `gherkinTags`' result
spreads into the runner's own `TestTagDefinition[]`, which every runtime assertion about the helper
(all of them about strings) is structurally unable to check;
`SharedLayerConstraint.types.ts` carries RUN-03's D-04 constraint, that a `shared` Layer whose error
channel is not `never` fails to compile while `perScenario`'s stays unconstrained — a claim about
what does NOT compile, which no running test can make;
`HookRegistrar.types.ts` carries ADR-EC-035/BEH-EC-027's own "compile error by arity" claim — that
`BeforeAllScenarios`/`AfterAllScenarios` reject a tag-expression argument the SAME way they are
already absent from `RuleDsl` — another claim about what does NOT compile; and
`Attachments.types.ts` carries ADR-EC-036/BEH-EC-028's POSITIVE half — `attach` reachable from a step
and from every per-Scenario hook kind, on both `Feature` and `Rule` dsls — while the NEGATIVE half
(`BeforeAllScenarios`/`AfterAllScenarios` rejecting `attach`) is asserted by
`scripts/verify-tsgo-gate.sh` assertion 14 instead, not by `@ts-expect-error` here: that diagnostic is
`@effect/tsgo`'s own plugin-injected `effect(missingEffectContext)`, which — like assertion 11b's
sibling per-Scenario-service case — does not interact with `@ts-expect-error`'s suppression the way a
plain structural TS error does (verified by hand, ADR-EC-036 records the finding). None is a stray
file to be "fixed" by renaming it to `.test.ts`, which would break `pnpm test` with
"No test suite found".

## §5 Acceptance scenario traceability

The rows below are enumerated from the tagged `.feature` files under
`packages/vitest/test/acceptance/`, which is the **only** directory in the
repository where a `.feature` file may carry a `@REQ-EC-NNN` tag. The `.feature`
files under `packages/gherkin/test/fixtures/` and
`packages/vitest/test/fixtures/` are parser and tag-scanning fixtures, and
`packages/gherkin/test/fixtures/README.md` states the prohibition for its own
corpus explicitly. `spec/scripts/verify-traceability.sh` check 4 enforces both
halves: it greps every `.feature` file in the repository for the tag pattern and
fails `pnpm verify:spec` naming any tag that has no row here.

The ids are allocated 1:1 against the 22 v1 requirements of the
`REQUIREMENTS.md` archived on the `planning-archive` branch, in the order written there, plus
`REQ-EC-023` for BEH-EC-019's step modules (audit remediation F-29),
`REQ-EC-024` for BEH-EC-023's per-Scenario `Random` seeding,
`REQ-EC-025` for BEH-EC-024's Outline-column-no-pattern-references delivery,
`REQ-EC-026` for BEH-EC-026's Scenario-level `@retry`,

written" rule. They are permanent: never renumbered and never reused
(AGENTS.md §6).

**All 31 are carried, and that is a counted claim rather than a stated one.**
`spec/scripts/verify-traceability.sh` check 5 derives it: it collects every
`@REQ-EC-NNN` occurrence across every `.feature` file in the repository WITH
duplicates, asserts each id occurs exactly once, asserts the distinct set is
exactly `REQ-EC-001` through `REQ-EC-031` with no gaps and nothing outside that

Check 4 cannot make that claim and never could — it asks only whether every tag

paragraph is prose; the count comes from the script.

Five rows above name a `.feature` file under
`packages/vitest/test/acceptance/negative/`, and every one of those files is
**starved**: deliberately broken, handed to no runner, **never emitted** as a
test, and never green. That is D-02's mechanism, not drift, and it is the same
shape `packages/vitest/test/tsgo-gate/` takes one level down — a committed
satisfied/starved pair rather than a script that edits a file and re-runs, so
there is no mutable working tree, no cleanup path that can leave the repository
dirty, and the flip is re-proven on every CI run instead of once at authoring
time.

The five requirements those rows carry — PARSE-03, MATCH-03, MATCH-04, MATCH-05
and RUN-02 — are all "fails loudly" behaviors, so a Scenario demonstrating one
DIRECTLY would be a red test. The tag therefore sits on the deliberately-failing
fixture, and
[`packages/vitest/test/acceptance/negative-requirements.test.ts`](../packages/vitest/test/acceptance/negative-requirements.test.ts)
drives each fixture and asserts the specific named error. **The wrapper is what
passes.** Every assertion in it makes TWO checks — that the failure happened,
and that it was the named one — because a fixture failing for an unrelated
reason satisfies the weaker check and reports nothing; that wrapper's mutation A
is the measurement rather than the argument.

The same rule the tsgo-gate exclusion note above states applies here one level
up: **those files are not suites, and renaming them would break the thing they
exist to prove.** They have no `.steps.test.ts` partner by design, which is the
one convention `packages/vitest/test/acceptance/README.md` establishes that this
subdirectory does not inherit, and
[`packages/vitest/test/acceptance/negative/README.md`](../packages/vitest/test/acceptance/negative/README.md)
says so in its own words.
